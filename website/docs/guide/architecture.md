# 아키텍처

InfraSketch 는 Next.js 15 (App Router) 하나로 화면과 서버를 함께 띄웁니다. 데이터는 PostgreSQL 에 Drizzle ORM 으로 저장합니다.

## 대화 한 차례의 흐름

사용자가 대화를 보내면 `POST /api/diagrams/[id]/chat` 이 받고, `server/chat/pipeline.ts` 의 `runChatTurn` 이 한 차례를 처리합니다. 응답은 **한 줄에 이벤트 하나(JSON Lines, `application/x-ndjson`)** 로 스트리밍됩니다. 스트림을 여는 공통 부분(첫 이벤트까지 버퍼링해 409·404 를 정하고, 연결이 끊기면 차례를 중단하는 일)은 `server/chat/stream.ts` 의 `streamTurn` 이 맡으며, 노드 질문 route 도 같은 함수를 씁니다.

```text
브라우저 (ui/chat/useChatTurn.ts)
  │ POST /api/diagrams/{id}/chat  { text }
  ▼
chat/route.ts ── 로그인·본문·소유권 확인 (401 / 400 / 404)
  │
  ▼
runChatTurn ── 구성도별 잠금 (이미 진행 중이면 409)
  1. 최신 버전 상태와 최근 대화 기록(차례마다 적용한 명령 포함)을 읽고, 계정의 망 지식을 읽는다
       (`server/network.ts` 의 `getNetworkKnowledge`. 못 읽으면 망 지식 없이 지금까지처럼 돈다)
  2. @멘션을 노드 ID 로 풀고, 사용자 메시지를 저장한다
  3. 의도를 정한다 (`server/chat/intent.ts` 의 `resolveIntent`)
       메시지가 “가정 변경:” 으로 시작하면 Clef 를 부르지 않고 무조건 구조 변경
       그 밖에는 Clef 로 분류 (구조 변경 / 질문 / 빠진 정보 답변 / 이력 / 재정렬 / 기타)
       문맥: 직전 AI 답변 + 아직 열린(‘모름’ 아닌) 빠진 정보 목록
       재정렬이면 Qwen 을 부르지 않고 안내 한 줄과 relayout 이벤트만 보낸 뒤 버전 없이 끝
  4. 그 밖의 의도는 의도에 맞는 프롬프트로 Qwen 을 스트리밍 호출한다
       (“현재 구성” 뒤에 망 지식이 있으면 `망 종류:`·`등급 규칙`·`기관 규칙`·`망 짝 규칙` 블록, 저장된 흐름 목록 `흐름:`, 지금 떠 있는 경고 `현재 경고:` 가 차례로 붙는다)
       ├ 구조 변경 경로: JSON Lines 를 줄 단위로 파싱
       │    → id 칸 정규화(normalizeAiCommand) → parseCommand(스키마 검증) → applyCommand(상태 적용)
       │    → 성공하면 cmd 이벤트, 실패하면 skip 이벤트. JSON 이 아닌 일반 글 줄은 say 이벤트로 보인다
       │    (`set_zone_type` 은 망 지식에 있는 종류 key 만 받고, 서버만 만드는 `set_link_guess` 는 AI 가 써도 건너뜀)
       │    (흐름 명령은 상태에 적용하지 않고 모아 둔다. 이미 있는 흐름 id 의 add_flow 는 update_flow 로 받는다)
       │    구조 변경인데 아무것도 반영하지 못했으면 다그치는 한 줄(RETRY_NOTE)을 붙여 한 번 다시 부른다
       └ 답변 경로: <think> 를 지운 글을 answer 이벤트로 흘림
  5. 적용된 명령이 있으면 먼저 비게 된 영역을 정리한다(settleTurn: pruneEmptyGroups)
     AI 가 `guess: true` 로 넣은 망연계마다 대신한 연결을 기록하고(`set_link_guess` cmd 이벤트)
     그 뒤 경고를 점검하고(checking, 망 지식 포함) 새 버전을 만든다
  6. 망연계가 끼어든 연결을 지나던 흐름 단계를 둘로 나누고(`rewriteFlows`),
     모아 둔 흐름 명령을 차례가 끝난 상태로 검사해 흐름 저장소에 저장한다
  7. 빠진 정보 수를 (망 지식으로 센 망 종류 줄을 포함해) 다시 계산하고 응답 메시지를 저장한 뒤
     (구조 변경 경로였으면 이번에 적용한 명령을 메타 `commands` 에 함께 저장)
     새 경고가 있으면 warnings 이벤트, 마지막으로 done 이벤트
```

### 대화 기록 재생

차례마다 최근 대화(그 세션의 사용자·AI 메시지, 최대 20개)를 모델에 함께 보냅니다(`server/chat/prompt.ts` 의 `replayHistory`). 모델은 기록 속 **자기 답의 모양을 그대로 따라 하기** 때문에, 무엇을 어떤 모양으로 보내는지가 결과를 크게 바꿉니다.

- 저장된 AI 답 글은 그 차례의 `say` 를 이어 붙인 일반 글이고, 낸 명령은 들어 있지 않습니다. 이 글을 그대로 보내면 모델이 명령 없이 일반 글로만 답하고(예: “업무망 구분 안 함” 요청에 0/3), `{"op":"say"}` 줄로만 바꿔 보내면 “say 한 줄만 쓰고 끝”을 따라 합니다(예: Kinesis 경로 그리기 0/3).
- 그래서 구조 변경 경로의 차례는 **실제로 적용한 명령**(앞 60개, `REPLAY_COMMANDS_MAX`)을 응답 메시지 메타 `commands` 에 저장하고, 다음 차례의 명령 모드 기록에는 `say` 줄 + 명령 줄(JSON Lines, 키 순서는 명령 예시대로)로 보냅니다. 이렇게 하면 두 사례 모두 3/3 입니다.
- 명령 모드 기록에서 구조 변경 경로였는데 아무것도 적용하지 못한 차례(빈 답, say 만 쓰고 멈춤, 전부 건너뜀)는 사용자 글과 함께 뺍니다. 답변·재정렬·이력 차례는 `say` 줄로 보내고, 명령을 저장하기 전의 옛 차례는 일반 글 그대로 둡니다. 답변 모드(질문·기타)에서는 모두 일반 글로 보냅니다.
- `commands` 는 서버 전용입니다. `server/chat/messages.ts` 의 `listMessages` 는 기본으로 이 칸을 빼고, 대화 파이프라인만 `withCommands` 로 읽습니다.
- 명령을 저장하기 전에 만든 메시지는 `npm run backfill:commands`(미리보기, `-- --apply` 로 적용)가 버전 차이로 채웁니다. 버전을 만든 차례는 바로 앞 버전과의 차이(`domain/diff.ts` 의 `commandsBetween`), 버전도 반영도 없는 명령 차례는 빈 목록(실패한 차례로 빠짐)이고, 흐름만 바꾼 차례처럼 되살릴 수 없는 것은 그대로 둡니다(`server/chat/backfill.ts` 의 `planCommandBackfill`). 이미 채운 메시지는 건드리지 않아 여러 번 돌려도 같습니다. 배포한 DB 에도 한 번 돌립니다.

### 흐름 명령과 `흐름:` 블록

- **프롬프트의 `흐름:` 블록**(`server/chat/prompt.ts` 의 `summarizeFlows`): 저장된 흐름이 있으면 “현재 구성” 뒤에 `흐름 <id> [user|system] "<이름>": 연결 id > 연결 id …` 한 줄씩 넣습니다. 이름은 사용자가 쓴 글이라 JSON 문자열로 감싸 줄바꿈이 새 줄을 만들지 못하게 합니다. 생성 프롬프트는 요청에 흐름 이야기가 없으면 흐름 명령을 쓰지 말고, 단계는 요청이 가는 방향으로만 쓰고 응답은 단계 대신 `result` 한 줄로 쓰며, 기존 흐름을 고치거나 지울 때는 이 목록의 id 를 쓰라고 지시합니다. 흐름 목록을 못 읽어도 차례는 흐름 없이 이어 갑니다.
- **남는 단계의 글은 지킵니다**(`domain/flows.ts` 의 `keepStepText`): `흐름:` 블록에는 연결 id 만 있어서, AI 가 `update_flow` 로 단계 전체를 다시 쓰면 남는 단계의 짧은 설명·설명 글을 새로 지어내곤 했습니다. 그래서 원래 흐름에도 있던 단계(같은 연결·같은 시작 노드)는 원래 글로 바꿔 저장하고 화면에도 그렇게 보냅니다. 사용자가 단계 글을 고쳐 달라고 할 때(`asksStepText`: “설명”·“문구”·“단계 글”)만 AI 글을 그대로 받습니다.
- **지웠다 다시 만든 연결은 원래 연결을 둡니다**(`domain/edgeCoalesce.ts` 의 `createEdgeCoalescer`): AI 가 한 차례 안에서 연결을 `remove_edge` 했다가 같은 두 노드 사이(같은 방향)에 `add_edge` 하면, 서버가 둘을 짝지어 원래 연결을 남기고 바뀐 값(이름·종류·전달물·방향)만 `update_edge` 로 반영합니다. 새 연결 id 를 가리키던 흐름 단계도 원래 id 로 바꿉니다. 그래서 지우기는 바로 반영하지 않고 이어 쓰기 직전과 차례 끝에 몰아서 반영하며(짝이 없으면 그때 지움), 화면에는 서버가 실제로 반영한 명령만 갑니다. 점검 스크립트(`eval:intent`)도 같은 도우미를 씁니다.
- **같은 망 안 연결에는 전달물·방향을 쓰지 않게** 프롬프트 예시를 일반 연결과 망을 넘는 연결로 나눴고, 이미 있는 노드·연결을 지웠다 다시 만들지 말라고(이중화로 옮길 때도 id·연결 유지), 구성만 바꾸는 요청에는 흐름을 고치지 말라고 지시합니다.
- **노드 attrs 칸 목록**(`prompt.ts` 의 `ATTR_LIST`): 카탈로그의 종류별 칸(`requiredAttrs`)을 “web_server, was, …: hostname(호스트명), cpu(CPU), …” 한 줄씩 생성 프롬프트에 넣고, os(운영체제)와 sw(설치 소프트웨어)를 구분하게 합니다. “모든 서버”, “WAS 전부”처럼 여러 대상을 말하면 조건에 맞는 노드를 빠뜨리지 말고 노드마다 `update_node` 를 내고, 그 칸이 없는 종류에는 쓰지 말라고 지시합니다.
- **모았다가 차례 끝에 저장**(`pipeline.ts`): `add_flow`·`update_flow`·`remove_flow` 는 구성도 상태에 적용하지 않고 모읍니다(이어 그리는 요청 사이에도 모읍니다). 구성 변경이 있으면 정리·경고 점검·버전 저장을 먼저 마치고, 그 **버전이 만든 최종 상태**로 `applyFlowOps` 가 검사해 저장하므로 같은 차례에 만든 연결도 단계로 쓸 수 있습니다. 거절된 흐름은 `skip` 하나로 알리고, 저장 자체가 실패해도 차례는 끝까지 마쳐 버전·응답 메시지·`done` 을 남깁니다(건너뜀 “흐름을 저장하지 못했어요”).
- **이미 있는 흐름을 `add_flow` 로 다시 쓰면 고치기로 받습니다**(`domain/commands.ts` 의 `createFlowRetarget`): 모델이 “흐름 고쳐 줘”에 기존 흐름 id 로 `add_flow` 를 쓰는 일이 있어 “exists” 로 거절되곤 했습니다. 대화 경로는 받는 순서대로 흐름 id 를 따라가며, 이미 있는(또는 이번 차례에 만든) id 의 `add_flow` 를 `update_flow`(이름·요약·결과·단계 교체, 출발 `origin` 은 기존 값)로 바꿔 적용합니다. 그 뒤 단계 글 지키기도 똑같이 적용됩니다. Claude Code 연동은 바꾸지 않고 거절합니다. 생성 프롬프트도 `흐름:` 목록에 있는 흐름을 고칠 때는 그 id 로 `update_flow` 를 쓰라고 지시합니다.
- **흐름만 바꾼 차례는 버전을 만들지 않습니다.** 정리·경고 점검·버전은 구성·가정을 바꾼 명령이 있을 때만 돌고, 흐름 명령은 `isStructural` 에서 빠집니다. 저장된 수는 `done.flows`(0보다 클 때)와 응답 메시지 메타의 `flows` 에 남고, 요약 칩의 “바꾼 곳”에는 세지 않습니다.

### 망 지식과 망연계 예상

계정 공통의 **망 지식**(망 종류와 기관 연결 규칙)을 보고, 서로 다른 망 사이에 망연계가 필요할 것 같으면 안내하거나 `AI 추정` 망연계를 넣어 그립니다. 판정이 아니라 **예상**이라서 문구는 늘 기관 규정과 방화벽 담당자에게 확인하라고 덧붙입니다.

- **망 종류와 등급**(`domain/network.ts`): 종류마다 key·이름·다른 이름·설명·등급(폐쇄·내부·경계·외부)이 있습니다. 두 종류 사이에 보통 필요한 방식(`requiredMethod`)은 **기관 규칙을 먼저, 없으면 기본 등급 규칙**(`GRADE_RULES`: 폐쇄망은 잇지 않음, 내부–외부는 망연계, 그 밖은 방화벽)으로 정합니다. 종류가 없거나 같은 종류면 규칙이 없습니다. 지식에 없는 종류(지운 것·숨긴 것)가 붙은 망은 **종류 없음**으로 칩니다.
- **프롬프트의 망 블록**(`prompt.ts` 의 `networkBlock`): 망 지식이 있으면 늘(영역이 아직 없는 처음 차례에도) `망 종류:`(key·이름·다른 이름·등급, 설명은 뺌), `등급 규칙(기관 규칙이 없을 때):`, `기관 규칙:`(보이는 종류끼리만, 없으면 “없음”), `망 짝 규칙:`(이 구성도에서 종류가 붙은 망 짝)을 넣습니다. 요약에는 영역마다 `type=<key>(확정|추정)`, 노드에는 `guess` 가 붙습니다. 규칙 문구는 AI 에게 `set_zone_type` 으로 망 종류를 붙이고, 망연계가 필요한 두 망 사이에는 `network_link` 노드를 `guess: true` 로 넣고, 사용자가 “방화벽으로 바로”라고 하면 따르되 `no_link:<망 id>--<망 id>` 가정을 남기라고 지시합니다. 사용자가 망연계를 넣어 달라고 했으면 `guess` 를 쓰지 않습니다.
- **통신 길과 경고**(`domain/networkRules.ts`): `crossingPaths` 가 방화벽·망연계·VPN 같은 경계 노드만 거쳐 이어진 길을 모읍니다. 길의 두 끝 망 종류로 필요한 방식을 구해 망연계가 필요한데 길에 망연계가 없으면 `link_expected`(망연계 필요 예상), 필요한 방식이 “보통 잇지 않음”이면 `link_unusual` 입니다. 둘 다 단계는 확인(`check`)이고, 같은 두 망 사이는 길이 여럿이어도 경고 하나(`link_expected:<망 id>--<망 id>`)입니다. 이 문구는 정해진 문구라서 이어 쓰지도 Qwen 으로 다듬지도 않고 늘 새로 계산합니다. 사용자가 **확정**한 “망연계 없음” 가정(`no_link:…`)이 있는 짝은 `link_expected` 를 끕니다. 대화로 받은 미확정 가정은 끄지 않습니다.
- **추정 망연계의 기록과 되돌리기**(`domain/linkGuess.ts`): 차례 끝에 `recordReplaced` 가 AI 가 넣은 `guess` 망연계가 대신한 연결을 `set_link_guess` 로 노드에 적어 둡니다(되돌릴 때 다시 그리려는 기록). 흐름의 단계가 그 연결을 지났으면 단계를 둘로 나누고(`splitFlowSteps`), 되돌리면 다시 합칩니다(`mergeFlowSteps`). 흐름 저장 실패는 차례나 되돌리기를 막지 않습니다.
- **“맞아요”·“아니에요”**(`server/linkGuess.ts`, 서버 액션 `confirmLinkGuessAction`·`rejectLinkGuessAction`): 맞아요는 `guess` 표시만 지웁니다. 아니에요는 망연계 노드를 지우고 원래 연결을 되살리며, 통신 길(`crossingPaths`)의 두 끝이 속한 망 짝을 찾아 `no_link:<망 id>--<망 id>` 가정을 **확정**으로 남깁니다. 방화벽이 망 밖에 있어도 짝을 찾습니다. 이 가정이 그 짝의 안내를 끄므로 경고 무시 목록(`ignoredWarnings`)에는 쓰지 않습니다. 가정 칩의 “지우기”(`removeNoLinkAction`)로 거절 기억을 지우면 안내가 다시 보입니다.
- **망 종류 확정**(`server/zoneType.ts`, `setZoneTypeAction`): 사람이 정하면 `source: "user"` 로 저장돼 AI 가 바꾸지 못합니다. 영역 정보 카드의 고르개(`ZoneTypePicker.tsx`)로 정하거나 지웁니다. 단, 그 key 가 지식에 더는 없으면(지운·숨긴 종류) 종류 없음으로 보고 AI 가 다시 붙일 수 있습니다(`applyCommand` 의 `netTypes` 옵션, 클라이언트 재생도 같은 옵션).
- **종류 key**(`server/network.ts` 의 `newTypeKey`): 새 종류의 key 는 `<이름 슬러그>-<무작위 8자>`(슬러그가 없으면 `net-<8자>`)이고, 지운 key 를 다시 주지 않습니다. 겹치면 최대 5번 다시 뽑습니다.

### 의도 분류 보호와 영역 정리

- **가정 변경 메시지**: 칩에서 가정 값을 바꾸면 화면이 `assumptionChangeMessage` 로 “가정 변경: …” 문장을 보냅니다. 서버는 이 접두어(`isAssumptionChangeMessage`)를 보면 Clef 에 묻지 않고 `structure_change` 로 정합니다. Clef 가 `layout` 으로 잘못 읽으면 요청이 버려지고 고정 위치만 풀리기 때문입니다. 환경·배포 방식처럼 영역이 달라지는 가정은 “새 영역을 먼저 만들고, 쓰던 노드를 옮기고, 남은 것을 지운다”는 순서를 함께 요청합니다.
- **JSON Lines 파서**(`server/llm/jsonl.ts` 의 `createJsonlParser`): 기본은 한 줄에 객체 하나지만, 모델이 객체 하나를 여러 줄로 나눠 써도 읽습니다. `{` 로 시작한 줄이 덜 닫혔으면 중괄호 깊이를 세면서(문자열 안의 중괄호는 세지 않습니다) 닫힐 때까지 줄을 모아 한 번에 파싱합니다. 모으는 글이 64KB 또는 200줄을 넘으면 깨진 줄 하나로 알리고 닫힐 때까지 버립니다. 모으는 도중에 그 줄만으로 온전한 JSON 객체인 줄이 오면 앞에 모은 것은 깨진 줄 하나로 알리고, 이 줄은 새 명령으로 정상 처리합니다. 그래서 깨진 객체 하나가 뒤따르는 온전한 명령을 삼키지 않습니다. 세 번째 인자 `onText` 를 주면 객체 밖의 일반 글(중괄호가 없는 글)은 깨진 줄 대신 자르지 않고 `onText` 로 넘깁니다. 대화 파이프라인은 이 글을 `say` 처럼 보여 주고 답 내용으로 저장하며(건너뜀으로 세지 않고 서버 로그에 줄 수만 남김), 중괄호가 섞인 글은 부서진 JSON 조각으로 보고 그대로 `bad_json` 건너뜀입니다. 흐름 제안·경고 문구·점검 스크립트는 `onText` 를 넘기지 않아 예전처럼 동작합니다.
- **id 칸 정규화**(`server/chat/normalize.ts` 의 `normalizeAiCommand`): `id`·`from`·`to`·`parent`·`target` 칸은 소문자로 바꾸고 `_` 를 `-` 로 바꿨을 때 id 형식(`^[a-z0-9][a-z0-9-]{0,63}$`)에 맞으면 그 값을 씁니다. 모든 명령이 같은 처리를 거치므로 노드 id 와 그것을 가리키는 칸이 서로 어긋나지 않습니다. 형식에 맞지 않으면 값을 그대로 두어 스키마가 거부합니다.
- **생성 프롬프트**(`server/chat/prompt.ts`): “JSON 객체 하나를 여러 줄로 나눠 쓰지 않는다”는 규칙이 있고, 이름(`label`·`sub`)은 한국어로 쓰되 제품명만 원어로 두도록 `"웹 서버 #1"`, `"공개 서브넷"` 같은 예시를 줍니다. 빠진 정보를 답하는 차례(`missing_info_answer`)에는 “값을 반영하는 명령은 한 줄에 JSON 하나로 쓰고, 사용자가 말한 대상마다 따로 `update_node` 를 낸다”는 안내를 채워야 할 정보 목록 뒤에 덧붙입니다. 노드 질문 프롬프트(`ASK_PROMPT`)는 답에서 노드 id 대신 이름을 쓰고, 구성에 없는 제품·기술 이름을 새로 꺼내지 말라고 지시합니다.
- **현재 경고 블록**(`prompt.ts` 의 `warningBlock`): 지금 화면에 떠 있는 경고(무시한 것 제외, 최대 30개)를 `현재 경고:` 아래 `- <노드 id> [연결 <연결 id>] "<문구>"` 한 줄씩 넣습니다. 모델이 경고를 모르면 “경고가 뜸” 같은 말에 원인을 짐작으로 답했기 때문입니다. 생성 프롬프트는 사용자가 경고를 말하거나 고쳐 달라고 하면 그 경고가 가리키는 노드·연결을 고치라고, 답변 프롬프트는 경고를 물으면 이 목록을 근거로 설명하라고 지시합니다.
- **경유 노드와 관계없는 이동**(`drawing/rules.ts`, Claude Code 의 `get_guide` 도 같은 글): 방화벽·WAF·로드밸런서·API 게이트웨이·망연계·VPN 처럼 통신이 거쳐 가는 노드를 넣으면 지킬 기존 연결을 지우고 “앞 노드 → 새 노드 → 뒤 노드”로 다시 이으라고(연결 없이 노드만 놓지 않게), 요청과 관계없는 노드를 다른 영역이나 이중화 묶음 밖으로 옮기지 말라고 지시합니다. 방화벽을 놓기만 하고 길은 그대로 둔 채 이중화 묶음까지 풀어 버린 사례가 있었습니다.
- **반영 못 한 차례의 안내**(`ui/chat/lines.ts` 의 `summaryText`): 차례가 정상으로 끝났는데 구성을 바꾼 것이 없고 AI 글도 없으면, 구성 변경 의도이거나 건너뛴 명령이 있을 때(재정렬 차례 제외) 요약 칩에 “요청을 반영하지 못했어요. 다시 말해 주세요.”를 보여 줍니다. 구성 변경 의도인데 “~추가합니다” 같은 글만 있고 바뀐 것이 없으면 “바꾼 곳이 없어요”를 보여 줘, 글만 보고 바뀐 줄 알지 않게 합니다(2026-11-11 결정, 이전에는 글이 있으면 알리지 않았습니다). 건너뛴 것도 없고 답도 없을 때만 “변경 사항이 없어요.”입니다.
- **반영 0 인 구성 변경의 재시도**(`pipeline.ts`): 구성 변경 의도인데 첫 응답(이어 쓰기 포함)이 아무것도 반영하지 못했으면, 같은 요청에 `RETRY_NOTE`(“앞 응답은 구성 명령 없이 끝났다. 요청대로 바꿀 명령을 낸다. 바꿀 것이 정말 없으면 이유를 say 한 줄로만 쓴다.”)를 붙여 **한 번만** 다시 부릅니다. 재시도도 출력 한도에 닿으면 똑같이 이어 씁니다. 진행 카드에는 `status` 의 `retry: true` 로 “다시 그리는 중”이 보이고, 그래도 바뀐 것이 없으면 위 안내가 뜹니다. 실제 사례(Kinesis 경로 그리기)에서 첫 시도 3/5 가 재시도 뒤 5/5 였습니다. 그 밖의 요약은 `노드 N · 연결 M · K곳 바꿨어요`(바꾼 것이 없으면 “바꾼 곳이 없어요”)로, 건너뛴 수는 화면에 보이지 않고 메타에만 남습니다.
- **이름 숫자 순서 배치**(`src/canvas/layout.ts`): `redundancy_group`·`k8s_cluster` 안에서 나란히 놓인 노드 중 이름이 같은 접두어에 숫자로만 끝나는 것(`웹 서버 #1`, `#2`, `API 2` 등)은 숫자 순서대로 놓으려 합니다. ELK 가 입력 순서를 지키지 않아, ELK 가 배치한 뒤 같은 줄 안에서 자리를 바꾸는 방식이며 **가능할 때만** 합니다. 바꾼 결과가 끝점이 아닌 노드를 가로지르는 연결을 새로 만들거나, 노드가 겹치거나, 서로 다른 연결이 같은 선 위에서 겹치게 되면 그 줄은 바꾸지 않고 ELK 의 순서와 경로를 그대로 둡니다. 안쪽 영역이 섞인 묶음은 건드리지 않고, 숫자가 없거나 접두어가 다른 이름(`Aurora Writer`, `주 DB`)은 대상이 아닙니다.
- **재정렬**: `layout` 의도는 노드·연결·영역을 바꾸지 않으므로 Qwen 호출도 새 버전도 없습니다. `relayout` 이벤트를 받은 브라우저가 고정 위치를 풀고 다시 배치합니다.
- **빈 영역 정리**(차례 끝 정리는 `server/chat/settle.ts` 의 `settleTurn` 하나로 모았고, 대화와 Claude Code 연동이 똑같이 씁니다. 정리한 영역 삭제 → 추정 망연계 기록 → 흐름 단계 나눔 순서도 같습니다): 적용된 명령이 있는 차례는 경고 점검과 버전 저장 전에 `domain/apply.ts` 의 `pruneEmptyGroups` 로 이번 차례에 비게 된 영역을 지웁니다. 차례 시작 때 이미 비어 있었거나 새로 만든 영역은 남기고, 안쪽부터 반복하므로 자식이 모두 지워진 부모도 함께 지워집니다. 지운 영역마다 `remove_group` 명령을 `cmd` 이벤트로 안쪽부터 보내, 브라우저가 서버와 같은 상태로 맞춥니다.

### 차례 끝의 경고 점검

적용된 변경이 있는 차례만 `server/chat/warnings.ts` 의 `checkWarnings` 로 위험한 구성을 점검합니다. 질문·이력 차례는 점검하지 않습니다.

1. **코드 규칙** (`domain/warnings.ts` 의 `evaluateRules`): 공개 구역의 DB·캐시(`db_public`), 이중화 묶음 밖의 서버·DB·로드밸런서·DB 중계·캐시(`spof`), 외부에서 방화벽 없이 서버·DB 로 바로 오는 연결(`no_firewall`, 인그레스·배스천은 예외), 원본 DB 없는 캐시(`cache_without_db`), 서로 다른 망 사이를 방화벽·망연계·VPN 없이 바로 잇는 연결(`network_direct`), 연결이 하나도 없는 경유 노드(`unused_passthrough`: 방화벽·WAF·L4/L7 로드밸런서·API 게이트웨이·NAT·VPN·망연계·CDN, “…을(를) 지나는 연결이 없어 아무 통신도 거치지 않아요”) 여섯 가지입니다. 망 지식이 있으면 여기에 망연계 필요 예상(`link_expected`)과 보통 잇지 않는 구간(`link_unusual`) 두 가지가 더해집니다(`evaluateNetworkRules`, 위 “망 지식과 망연계 예상” 참고). `spof` 는 단일 장애 지점 종류(`SPOF_KINDS`: 웹 서버·WAS·앱 서버·RDB·NoSQL·L4/L7 로드밸런서·DB 중계·캐시) 노드가 `redundancy_group` 안에 있지 않으면, 이중화 가정 값과 상관없이 켜집니다. 사용자가 이중화 가정을 "이중화 없음"으로 **확정**(의도)했을 때만 꺼집니다. 문구는 같은 종류가 그 노드 하나뿐이면 “…이(가) 1대뿐이라 멈추면 서비스도 멈춰요.”, 같은 종류가 2대 이상인데 묶음 밖이면 “…이(가) 이중화 묶음(VIP)에 들어 있지 않아 멈춰도 대신할 서버로 넘어가지 않아요.”입니다(이미 저장된 경고는 아래처럼 저장된 문구를 그대로 씁니다).
2. **Clef 판정** (`db_exposed`): 코드 규칙에 걸리지 않은 저장소 노드(DB·캐시·검색·DB 중계·파일 저장소) 중 **최대 5개**를 Clef `noul` 질문으로 "외부에서 직접 접근될 수 있는가"를 묻습니다. Clef 응답의 실제 `noul` 칸(예: `{ type: "noul", noul: 0.97 }`)을 먼저 읽고, 없을 때만 예전 추정 모양을 봅니다. 확률 0.8 이상이면 경고(`warn`), 0.5 이상이면 확인(`check`)입니다. 이 단계는 대기열을 포함해 **3초 상한**이고 재시도하지 않습니다(다음 차례의 의도 분류가 밀리지 않게). 판정이 실패하거나 시간을 넘기거나 5개 밖에 있는 노드는 **이전 판정을 그대로 이어 갑니다**.
3. **Qwen 문구**: 이번에 **새로 생긴 경고만**(`link_*` 는 정해진 문구라 뺌) Qwen 한 번 호출로 쉬운 문구(80자 이내)를 받습니다. 상한은 **8초**이고, 받지 못한 경고는 규칙에 정해진 문구를 씁니다. 이미 있던 경고는 저장된 문구를 다시 씁니다.

점검 결과는 버전 상태의 `warnings` 에 저장되고, 새 경고 중 사용자가 "의도된 구성"으로 무시하지 않은 것만 `warnings` 이벤트와 응답 메시지 메타로 알립니다. AI 단계가 실패해도 점검은 오류를 던지지 않습니다.

대화의 주의 칩은 새 경고만 세지 않습니다. 차례 시작과 끝의 화면 경고(무시 제외)를 `domain/warnings.ts` 의 `warningDelta` 로 비교해 새로 생긴 수·해결한 수·지금 모두를 `done.warningCounts` 와 메타 `warningCounts` 에 담고(새로 생기거나 해결한 것이 있을 때만), 칩은 “새 주의 2 · 주의 4 해결 · 지금 모두 6”처럼 0 인 항목을 빼고 보입니다(`ui/chat/lines.ts` 의 `warningsChip`). 경고가 그대로인 차례는 칩이 없고, 수가 없는 옛 메시지는 예전처럼 “주의 N”(새 경고 수)입니다.

### 빠진 정보 수

`domain/missing.ts` 의 `computeMissing` 이 노드 종류별 필수 항목(스펙·IP·hostname 등)과 흐름 연결(`request`·`async`)의 프로토콜/포트, 그리고 망 경계를 넘는 연결의 전달물·방향 중 빈 칸을 셉니다. 망 영역이 둘 이상이고 망 지식이 있으면 종류가 없는(또는 지식에 없는 종류의) 망도 “망 종류”라는 빠진 정보 한 줄로 셉니다. 이 줄은 영역 대상이라 AI 에게 넘기는 열린 항목에는 넣지 않습니다(AI 가 망 지식으로 추정합니다). 사용자가 체크리스트에서 "모름"으로 표시한 항목은 목록에는 남지만 수에서는 빠집니다. `done.missing` 은 늘 이 수를 담고, 응답 메시지 메타의 `missing` 은 적용된 변경이 있고 0보다 클 때만 남깁니다.

### 중단과 시간 초과

- 한 차례 전체는 **240초 상한**입니다(라우트 `maxDuration` 300초, 앞단 프록시도 300초 이상 허용해야 함). Qwen 이 출력 한도(16,000 토큰)에 닿아 `finish_reason=length` 로 끊기면, 지금까지 적용한 상태와 이어서 그리라는 안내(`CONTINUE_NOTE`)로 **최대 2번 더** 요청합니다. 앞 요청에서 새로 적용된 명령이 없으면 더 잇지 않고, 잘린 마지막 줄은 버립니다. 버전은 차례 끝에 한 번만 저장합니다. 브라우저 연결이 끊기면(라우트가 요청의 abort 를 차례에 전달) 같은 신호로 멈춥니다.
- 생성 도중 멈추면 상태를 `aborted` 로 정하고, 시간 초과일 때만 "응답 시간이 너무 길어 중단했어요" 오류를 보냅니다. 그 밖의 실패는 `error` 상태와 일반 오류 문구입니다.
- 중단·오류여도 그때까지 적용한 명령이 있으면 버전을 `aborted` 로 저장합니다. 이때 경고 점검은 이미 중단된 신호로 불러 **코드 규칙만** 돌리고, `db_exposed` 는 이전 판정을 이어 갑니다(DB 노출 경고가 사라지지 않게).
- 경고 점검 중에 중단·시간 초과가 나도 버전·메시지 메타·`done` 모두 `aborted` 로 맞춥니다.
- 전송이 끊겨 이벤트를 보내지 못해도 차례는 끝까지 돌아 버전과 메시지를 저장합니다.

이벤트 종류는 `server/chat/events.ts` 의 `ChatEvent` 에 정의돼 있습니다.

| 이벤트 | 의미 |
| --- | --- |
| `session` | 노드 질문에서 새 세션을 만들었을 때만, `start` 바로 앞에 옵니다. 세션 id·노드·노드 이름·제목·갱신 시각 |
| `start` | 차례 시작, 분류된 의도 |
| `relayout` | 고정 위치를 풀고 구성도를 다시 배치하라는 요청. 재정렬 의도일 때만 옵니다 |
| `status` | 진행 단계 (`thinking` → `drawing` 또는 `answering`, 변경이 있으면 끝에 `checking`). 이어 그리는 중이면 `part: {n, of}` 가 붙어 “이어서 그리는 중 (2/3)” 으로, 반영 0 이라 다시 그리는 중이면 `retry: true` 가 붙어 “다시 그리는 중” 으로 보입니다 |
| `say` | AI 가 남기는 한 줄 안내. 명령 모드에서 모델이 JSON 대신 쓴 일반 글 줄도 이 이벤트로 옵니다 |
| `cmd` | 서버에서 적용에 성공한 변경 명령(빈 영역 정리로 보내는 `remove_group` 포함). 브라우저는 이걸 받아 캔버스에 바로 그립니다 |
| `skip` | 깨진 줄이나 거부된 명령 |
| `answer` | 질문에 대한 답변 글 조각 |
| `warnings` | 이번 차례에 새로 생긴 경고(무시한 것 제외). 있을 때만, `done` 바로 앞에 옵니다 |
| `handoff` | 노드 질문에서 구성 변경을 요청했을 때, 사용자 글을 그대로 돌려줘 구성도 대화로 넘기게 합니다 |
| `open_history` | 이력 탭 열기 요청 |
| `error` | 사용자에게 보여 줄 오류 문구 (AI 미설정, 시간 초과, 진행 중인 차례 등) |
| `done` | 차례 끝. 새 버전 번호, `complete`/`aborted`, 적용·건너뜀·구성 변경(`changed`: 노드·연결·영역을 더하거나 고치거나 지운 명령만, 가정은 빼고)·빠진 정보 수, 노드·연결 수, 경고가 바뀌었으면 `warningCounts`(새로·해결·지금 모두). 구성 변경 요청인데 바뀐 구성도, 답한 글도 없으면 요약 칩에 “요청을 반영하지 못했어요. 다시 말해 주세요.”, 글만 있으면 “바꾼 곳이 없어요” 가 보입니다 |

응답 메시지의 메타(`MessageMeta`)에는 의도·적용·건너뜀 수·버전·상태·차례 끝의 노드·연결 수(`nodes`, `edges`)와 함께, 해당될 때만 `missing`(남은 빠진 정보 수)과 `warnings`(새 경고), `warningCounts`(경고 변화)가 저장됩니다. 그래서 대화 기록을 다시 열어도 경고 줄이 보입니다. 구조 변경 경로 차례에는 서버 전용 `commands`(적용한 명령 앞 60개, 위 “대화 기록 재생”)도 저장되며 화면으로는 내려가지 않습니다. 노드 질문에서 구성도 대화로 넘긴 답에는 `handoff` 가 남습니다.

## 노드에 대해 물어보기

설명 패널 맨 아래의 “이 노드에 대해 물어보기”나 노드 우클릭 메뉴의 같은 항목으로, 노드 하나를 두고 따로 질문을 이어 갑니다. `POST /api/diagrams/[id]/ask` (`{ nodeId, text, sessionId? }`) 가 받고 `server/chat/ask.ts` 의 `runAskTurn` 이 한 차례를 처리합니다. 응답 형식은 구성도 대화와 같은 ndjson 입니다. 이 차례는 **읽기 전용**이라 명령을 내지 않고 구성도 버전도 만들지 않습니다.

```text
runAskTurn
  1. 소유권 확인 (남의 구성도·세션은 404)
  2. sessionId 가 있으면 세션을 찾고, 세션의 노드와 nodeId 가 같은지 확인 (다르면 400)
  3. 노드가 지금 구성도에 있는지 확인 (없으면 409, 세션을 만들지 않음)
  4. 구성도별 잠금 (구성도 대화와 같은 잠금이라 둘이 동시에 돌지 않음, 이미 진행 중이면 409)
  5. 잠금 안에서 최신 상태를 다시 읽어 노드를 한 번 더 확인
     (기다리는 사이 구성도 대화가 지웠을 수 있음)
  6. 첫 질문이면 세션을 만들고 session 이벤트를 start 앞에 보낸다
  7. 의도를 분류한다 (Clef, 직전 답변만 문맥으로 쓰고 빠진 정보 목록은 비움)
       구조 변경이면 Qwen 을 부르지 않고 안내 한 줄(say)과 handoff 이벤트만 보냄
  8. 그 밖에는 Qwen 이 답변을 스트리밍한다 (answer 이벤트)
  9. 답변을 저장하고 done (version 은 null, applied·skipped 는 0). 세션 갱신 시각을 올린다
```

- **근거 범위**: 프롬프트(`buildAskMessages`)에는 대상 노드 요약(종류·SW·속성·연결된 노드), 저장된 설명(`cachedNodeExplanation`), 그 세션의 이전 대화만 들어갑니다. 설명 캐시는 패널이 보여 주는 것과 같은 규칙(서명이 맞을 때만, 사전의 최신 값을 덮어서)으로 읽으며 새로 만들지 않습니다. 설명을 읽다 실패하면 서버 로그에 남기고 설명 없이 답합니다. 근거에 없는 내용은 모른다고 답하게 합니다.
- **구성 변경 요청**: 질문 세션에서는 구성을 바꾸지 않습니다. 의도가 구조 변경이면 “구성을 바꾸려면 구성도 대화에서 말해 주세요.” 라고 답하고, `handoff` 이벤트로 사용자의 글을 그대로 돌려줍니다. 브라우저는 이 글을 구성도 대화로 넘길 수 있습니다. 응답 메시지 메타에는 `handoff: true` 와 넘길 글(`handoffText`)이 남아, 대화 기록을 다시 열어도 넘기기 버튼이 같은 글을 씁니다. 넘길 글이 비면 버튼 없이 안내만 보입니다. 의도 분류가 실패하거나 확신이 낮으면 질문으로 칩니다.
- **노드가 사라졌을 때**: 노드가 지금 구성도에 없으면 `NODE_GONE_MESSAGE` (“이 노드는 지금 구성도에 없어서 이어서 물을 수 없어요.”) 로 409 를 돌려줍니다. 질문 세션 화면도 같은 문구를 안내로 보입니다. 이미 만든 세션은 노드가 지워져도 목록에 남고, 만들 때의 노드 이름(`nodeLabel`)에 “(지워짐)”을 붙여 보입니다.
- **시간 제한**: 구성도 대화와 같은 240초 상한과 중단 규칙을 씁니다(`turnSignals`, `streamFailure` 를 `pipeline.ts` 와 함께 씁니다).

### 대화 세션

구성도 대화도 여러 개를 둘 수 있습니다. 세션이 없는 대화(`session_id` 가 NULL)는 지울 수 없는 “기본 대화”이고, “+ 새 대화”로 만든 구성도 대화 세션(`kind = diagram`)은 첫 메시지를 보낼 때 만들어집니다(`/chat` 의 `newSession: true`, 이어 쓸 때는 `sessionId`). 차례마다 AI 에 보내는 기록은 그 세션의 메시지만이고, 구성도 상태와 구성도별 잠금은 모든 세션이 함께 씁니다. 세션은 이름을 바꾸거나 지울 수 있고(지우면 메시지만 지워지고 버전은 남음, 차례가 진행 중이면 409), 잠금 안에서 세션을 다시 확인해 그사이 지워졌으면 아무것도 쓰지 않고 404 로 끝냅니다. 노드 질문에서 구성도 대화로 넘기는 글·참조·가정 칩은 마지막에 쓴 구성도 대화로 갑니다. 세션 목록(`GET /api/diagrams/[id]/sessions?kind=&cursor=`)은 묶음별로 최근 50개씩 “더 보기”로 이어 불러옵니다.

### 질문 세션

질문 세션은 노드 하나에 묶인 대화 한 묶음입니다. 첫 질문을 보낼 때 만들어지며, 제목은 첫 질문의 공백을 접고 60자로 자른 뒤 끝 공백을 지운 것입니다. 세션 목록은 최근에 쓴 순서로 50개(`SESSION_LIST_LIMIT`)까지만 불러옵니다. 구성도 대화는 세션이 없는 별도 대화로 그대로 남습니다.

- 대화 탭 위쪽의 세션 선택(`ui/chat/SessionPicker.tsx`)에서 “구성도 대화”와 질문 세션들을 오갑니다. 세션은 최근에 이어간 순서로 보이며 `노드 이름 · 제목` 으로 표시됩니다. 목록은 `useSessions.ts` 가 관리하고, 세션의 메시지는 `GET /api/diagrams/[id]/sessions/[sessionId]` (최근 100개) 로 불러옵니다.
- 서버가 `session` 이벤트로 새 세션의 id 를 알려 주기 전까지 화면은 대기 중인 새 세션으로 다룹니다.
- 질문 차례와 구성도 대화는 같은 잠금을 쓰므로, 한쪽이 진행 중일 때 다른 쪽을 보내면 409(진행 중) 오류가 납니다.

## 변경 명령

AI 는 구성도를 직접 그리지 않고 **작은 변경 명령**을 연달아 내보냅니다. 명령은 `domain/commands.ts` 의 zod 스키마로 검증합니다.

| 명령 | 하는 일 |
| --- | --- |
| `add_group` | 영역(VPC, 서브넷, 외부 서비스 묶음 등) 추가 |
| `add_node` / `update_node` / `remove_node` | 노드 추가·수정·삭제. `update_node` 의 `parent` 로 노드를 다른 영역으로 옮깁니다 |
| `add_edge` / `update_edge` / `remove_edge` | 연결 추가·수정·삭제 |
| `remove_group` | 영역 삭제. 안의 하위 영역·노드와 그에 닿은 연결까지 함께 지웁니다(없는 영역이면 거부) |
| `set_assumption` | 구조를 정한 가정(환경, 규모, 이중화 등) 기록. 망연계 거절 기억은 key 가 `no_link:<망 id>--<망 id>` 인 가정입니다 |
| `set_zone_type` | 망 영역(`network_zone`)에 망 종류 key 를 붙이거나(`null` 이면 지움) 합니다. AI 가 붙이면 `source: ai`(추정)이고, 사람이 확정한(`source: user`) 영역은 거부합니다 |
| `set_link_guess` | 망연계 노드가 AI 추정이라는 표시와, 그 노드가 대신한 연결(`replaced`, 되돌릴 때 다시 그림)을 기록하거나 지웁니다. **서버만 만드는 명령**이라 AI 가 쓰면 건너뛰고, “바꾼 곳”에 세지 않습니다 |
| `add_flow` / `update_flow` / `remove_flow` | 흐름 추가·수정·삭제. 구성 상태가 아니라 **흐름 저장소**에 적용하고, “바꾼 곳”에 세지 않습니다 |

`add_node` 에는 선택 칸 `guess`(망연계 노드를 추정으로 넣는다는 표시)가 있습니다. `add_edge`·`update_edge` 에는 선택 칸 `payload`(전달물: `api` | `file`)와 `direction`(방향: `one_way` | `two_way`)가 있습니다. 망 경계를 넘는 연결을 설명하는 칸입니다.

흐름 명령의 제한은 스키마가 정합니다: 이름 1~60자(앞뒤 공백 제거), `summary`·`result` 200자, 단계 1~20개(단계는 `edge`·`from`·`short`·`text`, 설명 `text` 120자), `origin` 은 `user` | `system`. 저장소는 이 검사를 믿고, 화면의 짧은 설명(`shortLabel`)은 12자를 넘으면 11자 뒤에 “…”를 붙입니다.

명령이 스키마에 맞지 않거나 없는 노드를 가리키면 버리고 `skip` 이벤트로 알립니다. 차례 전체가 멈추지는 않습니다.

경고(`warn`)와 빠진 정보 보고(`report_missing`)는 **일부러 명령으로 두지 않았습니다.** 생성 프롬프트도 이 둘을 내지 말라고 지시합니다. 경고는 차례 끝의 점검이, 빠진 정보는 `computeMissing` 이 상태에서 직접 계산합니다. AI 가 이런 줄을 내면 "지원하지 않는 명령"으로 건너뜁니다.

## AI 연동과 장애 대응

- **Qwen** (`server/llm/qwen.ts`): 대화 응답, 변경 명령, 경고 문구, 노드·연결 설명처럼 글을 만드는 일을 모두 맡습니다. OpenAI 호환 API 를 씁니다.
- **그리기 규칙 공용 모듈**(`server/drawing/rules.ts`): 노드·영역·연결 종류 목록, 종류별 attrs 칸, 명령 예, 그리기 규칙 글을 한곳에 두고 Qwen 시스템 프롬프트(`chat/prompt.ts`)와 Claude Code 의 `get_guide` 가 같은 글을 씁니다. 목록은 `domain/catalog` 에서 만들어 손으로 복사하지 않습니다. Qwen 출력 방식(JSON Lines·말하기·질문·이어 쓰기)에 관한 줄만 `prompt.ts` 에 남습니다.
- **망 지식**: 구조 변경 프롬프트에 망 블록이 붙습니다(위 “망 지식과 망연계 예상”). AI 는 망 종류를 추정해 붙이고 망연계를 추정으로 넣을 뿐, 판정은 코드(`evaluateNetworkRules`)가 합니다. 노드 질문(`ask.ts`)은 망 블록 없이 빠진 정보 수만 망 지식으로 셉니다.
- **Clef** (`server/llm/clef.ts`): 글을 만들지 않고 선택지 확률만 돌려주는 판정 모델입니다. 세 곳에 씁니다.
  - `classifyIntent`: 매 차례 앞의 의도 분류. 선택지는 구조 변경(노드를 다른 영역으로 옮기거나 필요 없는 것을 정리하는 요청, 흐름을 만들거나 고치거나 지우거나 보여 달라는 요청 포함)·질문(용어·구성·흐름·망에 대해 묻기만 하는 말, “브라우저 노드는 필요 없을까?”처럼 필요 여부·의견만 묻는 말 포함. “이 경로도 노드로 표현할 수 있을까?” 같은 부탁은 구조 변경)·빠진 정보 답변(연결의 전달물·방향을 알려 주는 말 포함)·이력·재정렬·기타입니다. 재정렬(`layout`)은 노드·연결·영역을 하나도 바꾸지 않고 화면 배치만 다시 해 달라는 요청일 때만 고릅니다. 직전 AI 답변(300자)과 열린 빠진 정보 목록(`openItems`)을 문맥으로 넘겨, 값만 알려 주는 답을 `missing_info_answer` 로 가립니다. 빠진 정보는 사용자 글·직전 AI 답에 이름이 나왔거나 참조한 대상(연결은 한쪽 끝)만 골라 "WAS: CPU·RAM" 처럼 대상별로 묶습니다(`server/chat/intent.ts` 의 `clefOpenItems`, 앞 20개·600자). 관계없는 항목을 길게 넘기면 질문과 값만 알려 주는 답의 확신도가 떨어지기 때문입니다. 대기열·재시도를 포함해 3초 상한이고, 확신도 0.6 미만이면 의도 없이 진행합니다.
  - `decide` + `noulProbability`: 경고의 `db_exposed` 판정. 예/아니오 확률을 읽습니다.
  - `decide` + `scoreValue`: 설명 품질 검사. "쉽고 간결함 / 보통 / 어렵거나 장황함"을 점수 0~2 로 읽습니다.

  `decide` 는 `capMs`(대기열·재시도를 포함한 전체 상한)와 `maxRetries` 를 받습니다. 경고와 설명 검사는 둘 다 `capMs` 3초, 재시도 0회로 부릅니다. `noulProbability` 는 `noul` 칸을 먼저 읽고 그 밖에 예전 추정 모양(`probability`, `probabilities.yes`, `choice`+`confidence`)을 받아 주며, `scoreValue` 도 여러 응답 모양을 받아 주고, 그 밖이면 `null` 을 돌려 판정을 건너뜁니다.

### 흐름 제안 (`server/flowSuggest.ts`)

`POST /api/diagrams/[id]/flows/suggest` (`{ auto? }`) 가 `suggestFlows` 를 불러, 구성도를 보고 요청 하나가 연결을 차례로 지나는 길 3~5개를 Qwen 으로 제안받아 “AI 제안”(미검수)으로 저장합니다. 구성도 버전은 만들지 않습니다. 사용자가 시작하는 흐름(`user`)과 배치·복제·백업 같은 시스템 흐름(`system`)을 섞도록 요청합니다.

- **자동 한 번 + 버튼**: 처음 그린 차례가 끝났는데 흐름이 없으면 화면(`useFlows`)이 자동(`auto: true`)으로 한 번 요청합니다. 모델을 부르기 전에 `diagrams.flows_suggested_at` 을 적어 두 번 돌지 않게 하고, 자동 제안이 하나도 못 만들면 적은 시각을 지워 다음에 다시 시도합니다. 버튼(“흐름 제안받기”)은 흐름이 있어도 덧붙이며, 이미 있는 흐름을 모델에게 알려 새 id 를 고르게 합니다. 흐름이 20개면 모델을 부르지 않고 상한 안내를 돌려줍니다. 연결이 없으면 만들 수 없어 실패로 돌려줍니다.
- **모델 호출 중에는 잠금을 쥐지 않습니다.** 처음 그린 직후 사용자가 보낼 다음 말을 막지 않기 위해서입니다. Qwen 요청은 하나당 30초 상한이고, 실패하거나 쓸 흐름이 없으면 한 번 더 요청합니다.
- **저장만 잠금 안에서** 그때의 최신 구성도로 다시 검사합니다(그 사이 지워진 연결을 가리키면 거절). 대화 차례가 잠금을 쥐고 있으면 1초씩 최대 5번 기다리고, 그래도 못 잡으면 “지금은 구성도를 그리는 중이에요” 로 끝납니다. 모델 출력에서는 `add_flow` 만 최대 5개 고르고, 형식 오류·겹치는 id·끊긴 흐름은 버립니다.

### 설명 생성 (`server/explain.ts`)

설명 패널은 `POST /api/diagrams/[id]/explain` 으로 노드·연결 하나의 설명을 받습니다. `explainTarget` 은 구성도 버전을 만들지 않고 대화 잠금도 잡지 않습니다. 캐시를 읽어 사전의 최신 값을 덮는 부분은 `cachedNodeExplanation` 으로 나뉘어 있어, 노드 질문도 만들지 않고 이 캐시만 읽어 씁니다.

1. 소유와 대상을 확인하고, 내용 서명(`signatureOf`)이 같은 캐시가 있으면 Qwen 없이 돌려줍니다. 노드는 이때 사전의 최신 정의를 덮어 보여 줍니다.
2. 노드는 용어 사전에서 정의를 찾습니다(`attrs.sw` → `sub` → 종류 이름 순). 사용자 사전이 비어 있으면 먼저 시드를 채웁니다.
3. Qwen 이 JSON 으로 설명을 씁니다. 노드는 역할과 ADR(결정·이유·대안·비용), 사전에 없으면 정의까지, 연결은 흐름·방식·이유·방화벽입니다. 형식이 틀리면 한 번 다시 요청합니다.
4. **품질 루프**: 길이 상한(`domain/explain.ts` 의 `LIMITS`)을 넘으면 그 지적만, 넘지 않으면 Clef 점수를 보고 1.7(`SCORE_MAX`, `server/explain.ts`)을 넘으면 "더 쉽고 짧게"를 지적해 **최대 2회** 다시 쓰게 합니다. 다시 쓰기가 실패하면 마지막으로 올바른 결과를 씁니다. Clef 가 실패하면 길이만 봅니다. 기준 1.7 은 실제 Clef 점수(쉽고 간결한 글 약 1.38, 장황한 글 약 1.93)를 보고 정했습니다.
5. 사전에 없던 용어는 AI 정의를 **미검수**(화면 배지 “AI 설명”)로 사전에 넣습니다(`sub` 에서 온 용어는 넣지 않습니다). 결과를 `explanations` 에 저장합니다.

Qwen 요청 하나는 30초 상한이고, 실패하면 "설명을 만들지 못했어요" 를 돌려줍니다. 사전 정의가 있으면 그 부분(`partial`)은 함께 보내 화면에 바로 보이게 합니다. 화면(`ui/explain/useExplanations.ts`)은 설명을 한 번에 하나씩 요청하며, 사용자가 부른 다시 쓰기·다시 시도 → 선택한 대상 → 서명이 바뀐 노드 순으로 차례를 정합니다. 실패는 자동으로 다시 하지 않습니다.

### 장애 대응 요약

- Qwen 설정이 없으면 대화 차례는 "AI 서버에 연결할 수 없어요" 오류로 바로 끝나고, 설명은 사전 정의만 보여 주는 실패로 돌아갑니다.
- Clef 가 없거나 확신도가 낮으면 의도 없이 일반 경로로 넘어갑니다. 경고는 코드 규칙과 이전 판정만으로, 설명은 길이 검사만으로 진행하므로 기능이 멈추지 않습니다.
- 경고 문구가 늦으면 정해진 문구를 씁니다.
- 한 차례에는 시간 제한이 있고, 넘으면 중단 상태로 저장합니다.

## Claude Code 연동 (MCP)

Claude Code 에서 내 구성도를 읽고 고치게 하는 길입니다. 앱이 `/api/mcp` 에 MCP 서버(Streamable HTTP)를 열어 두고, 이 길은 Qwen·Clef 를 부르지 않습니다. 서버는 상태를 기억하지 않아서(stateless), 요청마다 키로 계정을 확인하고 그 계정만 보는 서버를 새로 만들어 JSON 으로 답합니다. GET·DELETE 는 405 입니다. 로그인 세션 대신 라우트가 직접 키를 확인하므로 `/api/mcp` 는 로그인 검사에서 빼 둡니다(`middleware-paths.ts`).

### 도구 9개

모든 도구 설명은 “처음 그리기 전에 `get_guide` 를 먼저 읽으세요”로 끝납니다.

| 도구 | 하는 일 |
| --- | --- |
| `get_guide` | 그리는 법: 명령 형식, 종류 목록, 그리기 규칙, 표준 구성 패턴, 이 계정의 망 지식 |
| `list_projects` | 내 프로젝트와 그 안 구성도 목록(id·이름·최신 버전 번호) |
| `create_project` | 새 프로젝트를 만듭니다. 첫 구성도(버전 1)가 함께 생깁니다 |
| `list_diagrams` | 프로젝트 안 구성도 목록 |
| `create_diagram` | 프로젝트 안에 새 구성도(버전 1)를 만듭니다 |
| `get_diagram` | 구성도 최신 모습을 한 번에 읽습니다: 버전 번호, 영역·노드·연결·가정, 망 영역 종류, 망연계 추정, 흐름과 끊긴 흐름, 경고, 빠진 정보, 브라우저 주소 |
| `list_versions` | 변경 이력(최근 50개, 최신부터): 번호·시각·출처·요약 한 줄 |
| `apply_commands` | 명령을 적용합니다(최대 500개). `dry_run` 이면 검사만 하고 저장하지 않습니다 |
| `restore_version` | 예전 버전으로 되돌립니다. 새 버전이 하나 생기고 흐름은 되돌아가지 않습니다 |

일부러 넣지 않은 것은 프로젝트·구성도 삭제, 망 지식 편집, 계정 설정, Qwen 을 쓰는 기능입니다. 되돌리기 어려운 일은 브라우저에서만 하게 했습니다.

`get_guide` 글은 20,000자까지로 제한합니다. 넘으면 망 지식 부분을 줄여 맞춥니다(`mcp/read.ts`).

### 키 인증

- 키는 `isk_` 로 시작하는 43자 무작위 값입니다(`mcpKeys.ts`). 만들 때 한 번만 화면에 보이고, DB 에는 SHA-256 해시만 저장합니다. 한 계정에 10개까지, 이름은 40자까지입니다.
- Claude Code 는 `Authorization: Bearer <키>` 를 보냅니다. 라우트가 해시로 계정을 찾고, 찾으면 마지막 사용 시각을 갱신합니다. 키 모양이 아니면 DB 를 보지 않습니다.
- **키가 없으면 401**, **키가 틀렸거나 지워졌으면 403** 과 한국어 안내(“새 키를 만들어 다시 등록해 주세요”)를 돌려줍니다. 틀린 키에 401 을 주면 Claude Code(SDK)가 OAuth 를 찾아 나서서 안내가 보이지 않기 때문에 403 으로 나눴습니다. 키 확인 중 DB 오류가 나도 JSON 500 으로 답합니다.
- 키는 화면(`/claude-code`)에서 만들고 지웁니다. 지우면 그 키로는 바로 403 이 됩니다.

### 전부 아니면 하나도 아니게, 그리고 덮어쓰기 막기

`apply_commands` 는 명령을 전부 적용하거나 하나도 적용하지 않습니다(`mcp/apply.ts`). 하나라도 규칙에 어긋나면 어느 명령이 왜 안 되는지 알려 주고 아무것도 저장하지 않습니다. 대화 파이프라인과 같은 규칙을 쓰고, 차례 끝 정리(`settleTurn`)도 거칩니다.

- **`base_version`**: `get_diagram` 으로 읽은 버전을 함께 보냅니다. 구성을 바꾸는 호출에서 이 번호가 최신이 아니면 저장하지 않습니다. **흐름만 바꾸는 호출은 `base_version` 을 보지 않습니다.** 흐름은 버전 상태 밖의 `flows` 테이블에 따로 저장하기 때문입니다. 흐름만 바뀌면 구성도 버전은 그대로입니다.
- **저장 순간 다시 확인**: 읽을 때 최신이었어도 저장하는 사이 다른 쪽이 새 버전을 만들 수 있습니다. 그래서 버전 번호를 잠근 트랜잭션 안에서 `createVersion` 이 최신 번호를 한 번 더 확인합니다(`expectedLatest`, `lockLatestNumber`). 다르면 `StaleVersionError` 로 저장하지 않고 다시 읽으라고 알립니다. `restore_version` 도 같은 확인을 합니다.
- **이력 요약**: `summary` 를 비우면 “Claude Code에서 N곳 바꿈”(N 은 적용한 명령 수)이 남습니다. 최대 80자입니다.
- 버전은 `source: "mcp"`, `via: "mcp"` 로 저장되고, 이력 탭에 “Claude Code에서”로 보입니다.

### 그리기 규칙 공용 모듈

Claude Code 에게 알려 주는 그리기 규칙과 Qwen 프롬프트의 규칙이 어긋나지 않게, 종류 목록·attrs 칸·명령 예·규칙 글을 `server/drawing/rules.ts` 한곳에 모았습니다. Qwen 프롬프트(`chat/prompt.ts`)와 `get_guide`(`mcp/read.ts` 의 `buildGuide`)가 둘 다 이 모듈을 읽습니다. 차례 끝 정리도 `chat/settle.ts` 의 `settleTurn` 하나를 대화와 MCP 가 함께 씁니다.

### 열어 둔 화면이 바뀐 것을 알아채기

- 열어 둔 구성도는 탭이 보일 때 몇 초(3초)마다 `GET /api/diagrams/[id]/head` 를 묻습니다(`ui/useRemoteChanges.ts`). 답에는 최신 버전 `version`, **Claude Code 가 만든 최신 버전 `mcpVersion`**, 흐름 수와 마지막 수정 시각이 들어 있습니다.
- 브라우저는 `mcpVersion` 이 지금 보는 버전보다 클 때만 새로 불러옵니다. 브라우저가 스스로 만든 버전은 `mcpVersion` 을 올리지 않으므로 자기 저장을 바깥 변경으로 오해하지 않습니다. 흐름 수나 수정 시각이 바뀌면 흐름 목록만 다시 불러옵니다.
- 입력 중이거나 대화상자·이력 보기 중이면 끼어들지 않고 “Claude Code가 구성도를 바꿨어요 [불러오기]” 안내만 띄웁니다. 대화 차례 중에는 묻지도 않습니다.
- **유령 효과**: 불러오면 Claude Code 가 지운 노드·연결이 점선 테두리로 1초 동안 비쳤다가 사라집니다(`ui/GhostLayer.tsx`). 캔버스 “움직임”이 꺼졌거나 움직임 줄이기 설정이면 그리지 않습니다.

| `network_rules` | 계정 공통 기관 연결 규칙(마이그레이션 0007). 두 종류(`type_a` < `type_b` 로 정렬해 저장, 짝은 유일)·방식 `method`(`firewall` / `network_link` / `none`)·근거 `note`. 두 종류는 규칙을 만든 뒤 바꾸지 못하고 방식과 근거만 고칩니다 |
| `explanations` | 노드·연결 설명 캐시. 구성도·대상별로 하나이고, 내용 서명(`signature`)이 바뀌면 다시 만듭니다 |

버전 상태(`DiagramState`, `domain/types.ts`)는 JSON 으로 저장되며 다음을 담습니다.

- `groups`, `nodes`, `edges`, `assumptions`: 구성도 자체. 노드와 연결의 `unknown` 은 사용자가 "모름"으로 표시한 필수 항목 키 목록입니다. 망 영역에는 선택 칸 `netType`(`{ key, source: ai|user, confirmed }`), 망연계 노드에는 선택 칸 `guess`(추정 표시와 대신한 연결 기록)가 있습니다.
- `warnings`: 마지막 점검의 경고 목록(규칙·대상·수준·문구·안내). 코드 규칙 경고는 화면이 지금 상태로 다시 계산하고, 저장된 문구와 Clef 판정(`db_exposed`)만 여기서 가져옵니다.
- `ignoredWarnings`: 사용자가 "의도된 구성"으로 무시한 경고 ID 목록(`link_expected:a--b` 처럼 망 짝 id 가 붙은 형태도 받습니다). 망연계 “아니에요”는 여기에 쓰지 않습니다. 설명 탭의 주의할 점에서 다시 경고하도록 되돌릴 수 있습니다.

**흐름은 버전 상태에 넣지 않고 `flows` 테이블에 따로 저장합니다.** 그래서 이력에서 구성도를 되돌려도 흐름은 남습니다. 단계가 가리키는 연결이 사라지거나 방향이 어긋나는 **끊김은 저장하지 않고 불러올 때마다 최신 상태로 계산**합니다(`domain/flows.ts` 의 `checkFlow`: 없는 연결·시작 노드 불일치·앞 단계와 이어지지 않음·단방향 연결을 거슬러 감. 갈래는 허용). 끊긴 흐름은 대화로 다시 맞추거나 단계를 하나 지워 고칠 수 있고, 마지막 단계는 지울 수 없습니다.

마이그레이션은 `src/db/migrations` 에 있으며, 용어 사전·설명 테이블은 `0002`, 질문 세션 테이블과 `messages.session_id` 는 `0003` 에서 추가됐습니다. `0004` 는 이미 겹친 프로젝트·구성도 이름 중 나중 것에 ` 2`, ` 3` … 을 붙여 정리한 뒤 이름 유니크 인덱스를 만들고, `0006_flows` 는 `flows` 테이블과 `diagrams.flows_suggested_at` 을 추가하고, `0007_network_knowledge` 는 `network_types`·`network_rules` 테이블을 추가하고, `0008` 은 `mcp_keys` 테이블과 `diagram_versions.via`·`summary` 를 추가합니다.

`listMessages` 는 `sessionId` 가 null 이면 구성도 대화만, 아니면 그 세션의 것만 돌려줍니다. 그래서 `pipeline.ts` 의 대화 기록과 Clef 에 넘기는 직전 AI 답변(`lastAssistant`)에는 구성도 대화 메시지만 쓰이고, 질문 세션의 글은 섞이지 않습니다.

## 캔버스 그리기와 배치

- **연결선 층 순서**(`EdgeLayer.tsx`): 바닥 선 → 강조 덮개(`g.edge-emph`) → 움직임 층 → 화살표·클릭 영역·이름표 → 합친 이름표 순입니다. 노드를 고르거나 호버하면 닿은 연결을 강조 덮개에 자기 종류 모양 그대로 다시 그립니다. 선택은 2.5px 에 빛(glow)이 있고, 호버는 1.8px 에 빛이 없습니다. 강조 대상이 아닌 선은 `edge--under` 로 아래에 깔립니다.
- **흐림 단계**(`emphasis.ts`, `canvas.css`): 강조 대상이 아닌 연결은 0.12, 노드는 0.18, 연결된 노드가 하나도 없는 영역은 0.35 로 흐려집니다. 연결된 노드가 있는 영역은 `litZones` 가 골라 흐리지 않습니다.
- **같은 이름 합치기**(`edgeLabels.ts`의 `mergedLabels`): 고른 노드에 닿은 연결 중 이름표 글이 같은 것은 `<이름> ×N` 한 개로 합쳐 공유 줄기 위나 노드 옆에 보여 줍니다. 여러 개면 줄로 쌓고 선택 고리와 겹치지 않게 비킵니다. 이미지 저장은 합치지 않고 원래 이름표를 모두 그립니다.
- **영역 이름표 층**(`ZoneNameLayer.tsx`): 영역 이름표는 연결선 포털에서 연결선 위, 노드 아래에 그립니다. 글자 크기는 `clamp(11px, 10px/zoom, 20px)` 로 확대 비율에 따라 보정하고, 접힌 영역의 너비는 `collapsedGroupWidth`(`layout.ts`)가 정합니다.
- **16px 간격**(`layout.ts`): ELK 의 `edgeEdge`·`edgeEdgeBetweenLayers`·`portPort` 와 우회 통로 간격 `CHANNEL_STEP` 을 16px 로 둡니다. 16px 로 하면 교차가 늘거나 선이 저하(degraded)되거나 노드를 관통하면 기존 통로 경로(lane-route)로 되돌립니다.
- **배치 측정 회귀**(`layoutMetrics.ts`, `tests/unit/layoutRegression.test.ts`, `tests/fixtures/layout/baseline.json`): 교차 수(crossings), 나란한 길이(parallelPx), 공유 길이(sharedPx), 노드 관통(throughNode), 꺾임(bends), 가로세로 비(aspect), 영역 머리 교차(zoneHeadCrossings)를 고정 상태(25·50·100·200 노드)로 재서 baseline 이하인지 지킵니다.

## 흐름과 망 경계 그리기

- **망 경계 판정**(`domain/boundary.ts`): 노드의 가장 가까운 `network_zone` 조상 영역이 망입니다(`networkZoneOf`). 구성도에 망이 하나라도 있고 연결의 두 끝 망이 서로 다르면(한쪽이 망 밖이어도) 경계를 넘는 연결(`crossesBoundary`)입니다. 방화벽·망연계 솔루션(`network_link`)·VPN 은 경계를 정당하게 넘겨 주는 노드(`BOUNDARY_NODE_KINDS`)라서, 경계를 넘으면서 두 끝 어느 쪽도 이런 노드가 아니면 직접 넘김(`isDirectCrossing`)이고 `network_direct` 경고를 냅니다.
- **경계 표시**(`EdgeLayer.tsx`, `edgeLabels.ts`): 경계를 넘는 연결에는 선 위에 점(`boundaryDotAt`)과 태그(`tagSpots`)를 그립니다. 태그에는 전달물(API·파일)과 방향 화살표가 들어가고, 아직 안 정한 칸은 **빠진 정보**(전달물·방향)로 셉니다.
- **흐름 강조**: 흐름을 켜면 노드 선택을 풀고 그 흐름의 연결만 밝히며, 단계마다 “n. 짧은 설명” 이름표(`stepLabels`, `shortLabel`)를 붙입니다. 경계를 넘는 단계의 설명에는 “A망에서 B망으로 넘어가요(방화벽 거침)” 문장이 덧붙습니다(`crossingNote`). 망 지식이 있으면 망연계 예상에 걸린 단계에는 “망연계 필요 예상” 또는 “보통 잇지 않는 구간”이 덧붙습니다. 노드나 연결을 고르거나 Esc 를 누르면 흐름 보기를 풉니다. 입력칸·열린 메뉴 안의 Esc 는 흐름 보기를 풀지 않습니다.

## 흐름 탭

오른쪽 패널의 “흐름” 탭(`ui/flows/FlowPanel.tsx`)에서 흐름 목록, 이름 바꾸기·지우기, “맞아요”(AI 제안 표시 지우기), 끊긴 단계 안내와 “다시 맞추기”(구성도 대화로 `"<이름>" 흐름을 지금 구성에 맞게 다시 맞춰 줘` 를 보냄)를 다룹니다. 상태와 불러오기는 `useFlows.ts` 가 맡고, 대화 차례가 끝나면 다시 불러옵니다. 노드·연결 정보 카드(`NodeInfo.tsx`)에는 “이 노드를 지나는 흐름”(연결은 “이 연결이 들어간 흐름”) 이름 칩이 있어, 누르면 그 흐름을 켜고 흐름 탭으로 갑니다. 끊긴 단계만 걸친 흐름은 칩에 넣지 않습니다.

## 망 지식 화면

사이드바의 “망 지식”(`/network`, `src/app/(app)/network/page.tsx`)에서 계정 공통의 망 종류와 기관 연결 규칙을 봅니다. 서버 컴포넌트가 로그인을 확인하고(없으면 `/login`) 종류·규칙 목록을 읽어 `NetworkKnowledgePage` 에 넘기며, 편집은 `(app)/actions.ts` 의 서버 액션(`addNetworkTypeAction`·`updateNetworkTypeAction`·`resetNetworkTypeAction`·`setNetworkTypeHiddenAction`·`deleteNetworkTypeAction`·`upsertNetworkRuleAction`·`deleteNetworkRuleAction`)이 합니다.

- **망 종류**: 기본 제공 종류는 고치면 “고침” 표시가 붙고 처음 값으로 되돌리거나 숨길 수 있습니다. 직접 만든 종류는 지울 수 있고, 지우기 전에 쓰는 영역 수(`countNetworkTypeUsageAction`)를 알려 줍니다. 종류를 지우면 그 종류를 쓰던 규칙도 함께 지워집니다.
- **기관 규칙**: 두 종류와 연결 방식, 근거를 적습니다. 고칠 때는 두 종류를 잠그고 방식과 근거만 바꿉니다. 종류를 바꾸려면 지우고 새로 추가합니다.
- 구성도 화면에서는 영역 정보 카드가 망 종류(추정·확정 표시)를 보여 주고 고르개로 바꾸게 하며, 망연계 노드 카드에는 추정일 때 “맞아요·아니에요” 버튼이, 가정 칩에는 거절 기억의 “지우기”가 있습니다.
