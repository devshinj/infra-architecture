# B) CCTV·영상 관제 — 구성 지식

조사일 2026-11-11~12. "확인됨"은 출처 페이지·문서를 직접 열어 본문을 읽은 것만이다. 열지 못한 것은 5절에 따로 적었다.

---

## 1. 전형적인 구성

### 구성 ① 소규모 단독형 (매장·소규모 사옥, NVR 한 대)

구성요소: IP 카메라(PoE) 4~32대, PoE 스위치(또는 NVR 내장 PoE 포트), NVR, 모니터, (선택) 원격 열람용 모바일 앱.

- PoE 스위치 → IP 카메라 : 이더넷 케이블 한 가닥으로 전원 + 데이터(PoE, IEEE 802.3af/at/bt). 전원은 스위치→카메라 방향.
- NVR → IP 카메라 : ONVIF(HTTP/HTTPS, 80/443) 로 장치 검색·설정·PTZ 제어. 검색은 WS-Discovery(3702/UDP). 방향은 NVR 이 카메라로 접속.
- NVR → IP 카메라 : RTSP(554/TCP) 로 스트림 요청, 영상 자체는 RTP(UDP 또는 RTSP 연결 안에 실어 TCP)로 카메라→NVR 방향으로 흐른다. 흐르는 것: H.264/H.265 영상, 음성, 메타데이터.
- NVR → 모니터 : HDMI 등 영상 출력(네트워크 아님).
- 모바일 앱 → NVR : 제조사 방식(P2P 중계·포트포워딩·VPN). 표준이 없고 제조사마다 다르다(미확인, 5절).
- 아날로그 변형: 아날로그 카메라 → (동축 케이블) → DVR. DVR 이 디지털로 바꿔 저장한다. 기존 아날로그 카메라를 IP 망에 붙일 때는 비디오 인코더를 사이에 둔다(ONVIF Profile S 문서가 "camera or encoder" 를 영상 송신 장치로 든다).

### 구성 ② 중·대규모 온프레미스 VMS (사옥·공장·캠퍼스)

구성요소: IP 카메라 수백~수천 대, 현장 PoE 스위치(접근 스위치), 영상망 집선·백본 스위치, VMS 관리 서버, 녹화 서버 여러 대(+ 장애 대비 녹화 서버), 이벤트 서버, DB(SQL Server), 영상 저장 스토리지, 모바일 서버(웹·모바일 열람용), 관제 PC(VMS 클라이언트), 비디오 월.
아래 역할 구분은 Milestone XProtect 시스템 아키텍처 문서(2025 R2)에서 확인한 것이다. 다른 VMS 도 이름만 다르고 구조는 비슷하다고 알려져 있으나 다른 벤더 문서는 열지 못했다.

- 녹화 서버 → IP 카메라 : RTSP/RTP 또는 제조사 드라이버, ONVIF. 녹화 서버가 카메라로 **나가는** 연결을 맺고 영상·음성·메타데이터·I/O 이벤트를 가져온다(카메라→서버로 영상이 흐른다).
- 녹화 서버 → 영상 저장 스토리지 : 로컬 디스크 또는 SAN/NAS. 녹화본·아카이브 저장.
- 녹화 서버 ↔ 관리 서버 : 서버 간 내부 통신(설정 배포, 상태). 암호화 가능.
- 관리 서버·이벤트 서버·로그 서버 → DB(SQL Server) : 1433/TCP. 설정·알람·이벤트·로그 저장.
- 관제 PC(VMS 클라이언트) → 관리 서버 : 로그인·권한·설정(80/443).
- 관제 PC(VMS 클라이언트) → 녹화 서버 : 라이브·재생 영상과 PTZ 명령(Milestone 은 7563/TCP). **영상은 관리 서버를 거치지 않고 녹화 서버에서 직접 온다.**
- 관제 PC → 이벤트 서버 : 알람·이벤트·지도 데이터(Milestone 은 22331/TCP).
- 비디오 월 : 월 화면을 띄우는 PC 도 VMS 클라이언트다. 운영자가 배치를 바꾸면 → 관리 서버가 DB 에 저장하고 월 클라이언트에 알림 → 월 클라이언트가 새 배치를 받아 적용.
- 모바일·웹 클라이언트 → 모바일 서버 → 녹화 서버 : 모바일 서버가 녹화 서버에서 스트림을 받아 코덱·형식을 바꿔 내보낸다(Milestone 은 8081 HTTP / 8082 HTTPS). 이렇게 하면 "녹화 서버는 인터넷에 붙지 않는다"고 문서가 적는다.
- 장애 대비 녹화 서버 ↔ 녹화 서버 : 상태 확인(폴링), 장애 시 녹화 인계, 복구 후 DB 병합. 콜드 스탠바이(여러 대 감시)·핫 스탠바이(한 대 전담) 두 방식.
- 다지점: 원격지 녹화 서버 → 중앙 녹화 서버 → 관제 PC (Milestone Interconnect). 원격지만 녹화 / 중앙만 녹화 / 양쪽 녹화 / 회선이 끊긴 뒤 나중에 가져오기를 고를 수 있다.

### 구성 ③ 지자체 CCTV 통합관제센터 (공공)

구성요소: 현장 카메라(방범·교통·재난, 함체 안에 스위치·전원), 자가통신망 또는 임대 회선, 관제센터 영상망(단독망), VMS, 저장장치, 인공지능 기반 관제시스템(단말형/서버형), 영상검색시스템, 영상반출시스템, 개인정보 비식별처리 시스템, 관제 PC, 비디오 월, 비상전원·항온항습기, 재난안전상황실, 외부 연계 기관(경찰 112·소방 119 등).
구성요소 이름은 「지방자치단체 영상정보처리기기 통합관제센터 설치·운영에 관한 고시」(행정안전부고시 제2026-31호) 제2조·제3조가 쓰는 말 그대로다.

- 현장 카메라 → 관제센터 VMS(녹화 서버) : 자가망·전용회선 위의 RTSP/RTP. 영상이 센터로 흐른다.
- 관제센터 망 ↔ 인터넷·업무망·행정망 : **잇지 않는 것이 원칙**(고시 제3조①3호 "분리된 단독망 구성을 원칙"). 연계가 필요하면 「국가 정보보안 기본지침」을 따른다(같은 조 4호) → 구성도에는 망연계 장비·통제 구간으로 그린다.
- 관제 PC → VMS : 라이브 관제, PTZ 조작(고시 제13조: 생명·신체·재산 보호와 관련될 때만 회전·확대·축소).
- 서버형 AI 관제시스템 → VMS/녹화 서버 : 센터에 모인 영상을 받아 분석 → 이벤트를 관제 화면에 올린다. 단말형은 카메라·함체에서 분석하고 결과(메타데이터·이벤트)만 올린다.
- 통합관제센터 ↔ 재난안전상황실 : 영상정보 등 재난관리정보 공유(재난안전법 제74조의5④, 고시 제7조·제10조).
- 다른 공공기관 카메라 → 통합관제센터 : 관할 지역 공공기관 카메라를 연계·통합 관제(법 제74조의5③, 고시 제4조).
- 통합관제센터 → 경찰·소방 등 : 영상 제공(영상반출시스템, 스마트시티 통합플랫폼의 112·119 연계). 플랫폼 연계의 1차 출처는 열지 못했다(5절).
- 저장: 수집일부터 30일 이내 보관이 원칙(고시 제14조).

### 구성 ④ 영상 분석 결합형 (CV 파이프라인 + VLM)

구성요소: 카메라 또는 VMS(스트림 공급), 스트림 수집/디코딩, 실시간 CV(객체 검출·추적), VLM 추론 서버(GPU), 임베딩, 메시지 브로커(Kafka·Redis Streams·MQTT), 행동 분석, 알림 검증, 검색 저장소(Elasticsearch), 에이전트(LLM), 운영자 화면.
NVIDIA VSS Blueprint 문서(3.3.0)와 DeepStream 문서(9.2)에서 확인한 흐름이다.

- 카메라/VMS → 분석 서버 : RTSP(라이브) 또는 영상 파일. 분석 서버가 스트림을 당겨 온다.
- 디코드 → 배치(streammux) → 추론(TensorRT/Triton) → 추적 → 화면 표시(OSD) → 메시지 변환·브로커 전송 : DeepStream 파이프라인 단계.
- 실시간 CV → 메시지 브로커 : 프레임별 메타데이터(검출·추적 결과).
- 메시지 브로커 → 행동 분석 : 속도·방향·경로 계산, 선 넘기(tripwire)·관심구역(ROI) 규칙으로 사건(incident) 생성.
- 행동 분석 → 알림 검증 서비스 → VLM : 알림 시각의 영상 구간을 가져와 VLM 이 다시 본 뒤 confirmed / rejected / unverified 로 판정.
- 알림 검증 → Elasticsearch(저장), 선택적으로 Kafka 재발행.
- 실시간 VLM : 영상에 설명문(caption)을 달고 사건·이상을 찾는다. 결과는 메시지 브로커로.
- 에이전트 → 각 서비스 : REST·MCP 로 분석 결과·사건 기록·영상 조각을 가져와 보고서·질의응답·영상 검색.
- 배치: 데이터센터 GPU, 엣지 장비(DGX Spark·IGX Thor·AGX Thor), Kubernetes(Helm). VSS 문서는 "신뢰할 수 있는 격리된 네트워크에서 돌릴 것, 인증·TLS 종료·속도 제한·외부 접근 통제는 바깥 인프라가 맡는다"고 적는다.
- 프레임을 몇 초 단위로 몇 장 뽑아 VLM 에 넣는지는 문서에서 확인하지 못했다(5절).

### 구성 ⑤ 외부·웹 열람 (스트림 변환)

- 카메라/VMS → 미디어 게이트웨이(예: MediaMTX) : RTSP·SRT 등으로 들어온다.
- 미디어 게이트웨이 → 웹 브라우저 : HLS(HTTP) 또는 WebRTC 로 바꿔 내보낸다. MediaMTX 문서는 "스트림이 한 프로토콜에서 다른 프로토콜로 자동 변환된다"고 적는다. 브라우저는 RTSP 를 직접 재생하지 못하므로 이 변환 단계가 들어간다(브라우저 미지원 자체는 1차 출처로 확인하지 않음).
- 거점 간 장거리 전송 : SRT(UDP 위, 재전송·암호화). IETF 문서는 만료된 개인 제출 초안이며 RFC 가 아니다.
- VMS 를 쓰면 모바일 서버(구성 ②)가 같은 역할을 한다.

## 2. 구성요소 사전

| 요소 | 역할 | 놓이는 곳 | 구성도에 적을 속성 |
|---|---|---|---|
| IP 카메라 | 영상을 찍어 압축해 네트워크로 보낸다 | 현장(영상망 말단) | 대수, 해상도, 코덱(H.264/H.265), PoE 여부, ONVIF 프로파일, 모델 |
| PTZ 카메라 | 원격으로 회전·확대·축소한다 | 현장 | 대수, 광학 줌 배율, 프리셋 |
| 아날로그 카메라 + DVR | 동축 케이블로 영상을 보내고 DVR 이 디지털로 저장 | 현장~기계실 | 채널 수, 저장 용량 |
| 비디오 인코더 | 아날로그 영상을 IP 스트림으로 바꾼다 | 현장~기계실 | 채널 수 |
| PoE 스위치 | 카메라에 데이터와 전원을 함께 준다 | 현장 함체·층 통신실 | 포트 수, PoE 규격(af/at/bt), 총 전력 |
| 함체 | 현장 스위치·전원·통신 장비를 넣는 외함 | 옥외 현장 | 수량, UPS 여부 |
| NVR | IP 카메라 영상을 받아 저장·재생하는 일체형 장비 | 기계실·관제실 | 채널 수, 디스크 용량, 보관 일수 |
| VMS 관리 서버 | 설정·사용자 인증·권한·규칙을 맡는 VMS 중심 | 관제센터 서버 구역 | SW 이름·버전, 이중화 여부 |
| 녹화 서버 | 카메라에서 스트림을 가져와 저장하고 클라이언트에 준다 | 관제센터 서버 구역(영상망과 맞닿음) | 대수, 서버당 카메라 수, 보관 일수 |
| 장애 대비 녹화 서버 | 녹화 서버가 죽으면 녹화를 넘겨받는다 | 녹화 서버와 같은 구역 | 방식(핫/콜드), 대수 |
| 이벤트 서버 | 이벤트·알람·지도·외부 연동을 모아 처리 | 서버 구역 | SW·버전 |
| 영상 저장 스토리지 | 녹화본을 쌓아 두는 저장소 | 서버 구역·스토리지망 | 용량, 보관 일수, RAID |
| 모바일 서버 / 미디어 게이트웨이 | 스트림을 웹·모바일용으로 바꿔 내보낸다 | DMZ 또는 경계 구역 | 지원 프로토콜(HLS/WebRTC), 동시 접속 수 |
| 영상 분석 서버(서버형) | 센터에 모인 영상을 AI 로 분석 | 서버 구역(GPU) | GPU 종류·수, 분석 채널 수, 모델 |
| 엣지 AI 카메라(단말형) | 카메라·함체에서 분석해 결과만 올린다 | 현장 | 분석 종류, ONVIF Profile M 여부 |
| VLM 추론 서버 | 영상 구간을 읽고 글로 설명·판정 | 서버 구역(GPU) | 모델 이름, GPU 수 |
| 메시지 브로커 | 분석 메타데이터·이벤트를 전달 | 서버 구역 | 종류(Kafka/MQTT/Redis Streams) |
| 관제 PC | 운영자가 라이브·재생·알람을 보는 VMS 클라이언트 | 관제실(관제망) | 대수, 모니터 수 |
| 비디오 월 | 여러 화면을 이어 붙인 대형 표시 장치 | 관제실 | 화면 수(예: 2×4), 월 컨트롤러 |
| 영상반출시스템 | 수사기관·정보주체 요청 영상을 기록을 남기며 내보낸다 | 관제센터 | 반출 매체, 암호화 여부 |
| 개인정보 비식별처리 시스템 | 반출·열람 영상에서 제3자를 가린다 | 관제센터 | SW 이름 |
| 재난안전상황실 | 통합관제센터와 영상·재난정보를 공유하는 상황실 | 지자체 내부(다른 망일 수 있음) | — |

## 3. 망·보안 관점

### 3.1 망 배치

- **영상망(카메라망)**: 카메라·PoE 스위치·녹화 서버의 카메라 쪽 포트가 붙는 망. 업무망과 VLAN 또는 전용 장비로 나눈다. 대역폭을 많이 쓰고, 카메라는 현장에 노출된 단말이어서 누가 포트를 뽑아 꽂기 쉽다 → 802.1X(포트 기반 접근 통제)·MAC 고정을 건다. Axis OS 문서가 카메라의 802.1X(EAP-TLS) 지원을 적고 있다.
- **관제망**: 관제 PC·비디오 월·VMS 서버가 붙는 망. 영상망과는 녹화 서버(양쪽에 발을 걸침) 또는 방화벽으로 잇는다.
- **업무망·인터넷과의 사이**: 기존 seed 의 `iot-net ↔ business-net = network_link` 와 같은 결. 지자체 통합관제센터는 고시가 "인터넷 및 업무·행정망과 분리된 단독망"을 원칙으로 못 박았다.
- **외부 열람**: 녹화 서버를 인터넷에 직접 내놓지 않는다. 모바일 서버·미디어 게이트웨이를 경계 구역에 두고 그것만 바깥에서 닿게 한다(Milestone 문서의 권장 구조).
- **분석 서버**: 영상망/관제망 안쪽에 둔다. VSS 문서는 격리된 신뢰망에서 돌릴 것을 전제한다. 외부 LLM·VLM API 로 영상을 보내는 구성은 개인영상정보의 제3자 제공·위탁 문제가 걸린다(표준지침 제40조·제43조).

### 3.2 암호화·인증

- 표준 개인정보 보호지침 제47조 3호: "네트워크 카메라의 경우 안전한 전송을 위한 암호화 조치, 개인영상정보파일 저장시 비밀번호 설정 등".
- 기술 수단: RTSPS(TLS 위 RTSP, 기본 포트 322) + SRTP. ONVIF 스트리밍 규격(v26.06)은 "SRTP 를 쓸 때 RTSP 에는 TLS 를 써야 한다"고 적는다. 방화벽 통과용으로 RTP/RTSP/HTTPS/TCP 와 WebSocket 터널도 규격에 있다.
- Axis 문서 기준 카메라 기본 포트: HTTP 80, HTTPS 443, RTSP 554, RTSPS 322, WS-Discovery 3702/UDP, NTP 123/UDP. 방화벽 규칙을 적을 때 쓸 수 있다.

### 3.4 망분리 완화(N²SF)와의 관계

- 통합관제센터 고시는 2026-05-11 에 제정됐고, 그 안에 "단독망 구성을 원칙으로 할 것"이 들어 있다. 즉 **지자체 통합관제센터에 한해서는 일률 망분리 폐지와 별개로 고시 자체가 분리 원칙을 둔다.**
- 다만 "원칙"이고, 다른 망과의 연계는 금지가 아니라 「국가 정보보안 기본지침」 준수 조건으로 열려 있다(제3조①4호). 무엇을 거쳐 이어야 하는지(망연계 장비·일방향 전송 등)는 고시에 없고 그 지침에 맡겨져 있다.
- 고시가 인용하는 이름은 「국가 **정보보안** 기본지침」이다. 앞선 조사에서 확인했다는 「국가 **사이버보안** 기본지침」(2026-05-01)과 이름이 다르다. 같은 문서의 개명 전 이름을 고시가 그대로 쓴 것인지, 별개 문서인지는 국정원·국가사이버안보센터 원문을 열지 못해 확인하지 못했다.
- 통합관제센터가 아닌 일반 공공기관·민간의 CCTV 망은 이 고시의 대상이 아니다. 거기서는 개인정보 보호법 제25조⑥·표준지침 제47조의 "접근 통제·전송 암호화" 수준이 요구되고, 망을 나누라는 문구는 확인하지 못했다.

### 3.5 흔한 실수

1. 관제 PC 가 영상을 관리 서버에서 받는 것으로 그린다 → 실제로는 녹화 서버에서 직접 받는다.
2. 카메라가 녹화 서버로 "밀어 넣는" 화살표로 그린다 → 접속은 녹화 서버(또는 NVR)가 카메라로 건다. 영상은 반대로 흐르므로 선에 "RTSP 요청 / RTP 영상"을 함께 적는 편이 정확하다.
3. NVR·녹화 서버를 포트포워딩으로 인터넷에 직접 내놓는다.
4. 카메라를 업무망 스위치에 섞어 꽂는다.
5. RTSP(554)를 암호화된 것으로 가정한다 → 암호화는 RTSPS/SRTP 를 따로 켜야 한다. Axis 문서 기준 기본값은 꺼져 있다.
6. 브라우저가 RTSP 를 바로 재생한다고 그린다 → 변환 서버(HLS/WebRTC)가 필요하다.
7. 카메라에 녹음을 켠다(법 제25조⑤ 위반), 보관 기간을 정하지 않는다.
8. 통합관제센터 영상망을 행정망·인터넷에 방화벽 하나로 바로 잇는다(고시 제3조).
9. ONVIF Profile S 만 보고 H.265·메타데이터가 된다고 가정한다 → 그것은 Profile T·M 이다. Profile S 는 폐지 절차 중이다(적합성 제출 마감 2027-03-31).

## 4. 구성도를 그리는 AI 에게 줄 지침 후보

1. IP 카메라는 PoE 스위치를 거쳐 영상망에 붙인다. 카메라를 업무망·사무망에 직접 두지 않는다.
2. 카메라와 저장 장치 사이에는 반드시 녹화 주체(NVR 또는 VMS 녹화 서버)를 둔다. 수십 대 이하 단일 거점은 NVR, 그 이상이거나 다지점이면 VMS(관리 서버 + 녹화 서버 여러 대)로 그린다.
3. 카메라–녹화 서버 선은 "RTSP/RTP"로 적고, 제어·설정은 "ONVIF"로 따로 적는다. 접속은 녹화 서버가 카메라로 건다.
4. 관제 PC 의 영상 선은 녹화 서버에서, 로그인·설정 선은 관리 서버에서, 알람 선은 이벤트 서버에서 온다.
5. 비디오 월은 월 컨트롤러(또는 월용 VMS 클라이언트)를 거쳐 잇는다. 카메라나 녹화 서버에 직접 잇지 않는다.
6. 웹·모바일·타 기관 열람은 경계 구역의 모바일 서버나 미디어 게이트웨이(RTSP→HLS/WebRTC)를 거쳐 잇는다. 녹화 서버를 인터넷에 직접 내놓지 않는다.
7. 영상망과 업무망 사이는 잇지 않거나 통제 장비(방화벽·망연계)를 거친다. 지자체 통합관제센터면 영상망을 인터넷·업무망·행정망과 분리된 단독망으로 그리고, 연계가 필요하면 망연계 구간을 둔다.
8. 영상 분석은 두 자리 중 하나로 그린다: 카메라·함체 안(단말형, 결과 메타데이터만 올라감) 또는 센터의 GPU 서버(서버형, 녹화 서버나 카메라에서 스트림을 받음).
9. VLM 분석은 "스트림 → (CV 검출·규칙) → 알림 → VLM 검증 → 이벤트 저장/관제 화면" 순서로 잇고, VLM 추론 서버에는 GPU 속성을 적는다. 분석 결과는 메시지 브로커를 거쳐 흐른다.
10. 영상을 기관 밖 AI API 로 보내는 선은 그리기 전에 사용자에게 확인한다(개인영상정보의 제3자 제공·위탁에 해당할 수 있다).
11. 공공 CCTV 구성도에는 저장 장치에 보관 일수(기본 30일 이내)를 적고, 영상 반출 경로에는 비식별 처리(마스킹) 단계를 둔다.
12. 통합관제센터는 재난안전상황실, 경찰(112)·소방(119)과의 영상 연계 선을 외부 연계로 그리고 "예상"임을 밝힌다.

### 망 seed 에 더할 후보 (제안, 코드는 고치지 않음)

- 망 종류: `video-net` "영상망"(별칭: 카메라망, CCTV망, 영상감시망) — closed, separated=true. 지금 `iot-net` 설명에 "센서나 카메라"가 들어 있어 겹친다. 따로 둘지 `iot-net` 별칭으로 넣을지 선택이 필요하다.
- 망 종류: `control-center-net` "통합관제망"(별칭: 관제망, 관제센터망, 영상 단독망) — closed, separated=true.
- 짝 규칙 후보: 영상망 ↔ 업무망 = network_link / 영상망 ↔ 인터넷 = none / 통합관제망 ↔ 행정망(admin-net, local-gov-net) = network_link("단독망이 원칙이고 연계는 국가 정보보안 기본지침에 따라요") / 통합관제망 ↔ 인터넷 = none / 영상망 ↔ 통합관제망 = firewall 또는 direct(녹화 서버가 양쪽에 붙음).
- 노드 종류 후보(catalog 에 없음): 카메라, NVR/녹화 서버, 관제 PC, 비디오 월, 영상 분석 서버. 지금은 `generic` 으로만 표현된다.

## 5. 확인하지 못한 것·출처가 갈리는 것

- **국정원 「국가 정보보안 기본지침」/「국가 사이버보안 기본지침」의 영상 관련 조항**: 원문을 열지 못했다(ncsc.go.kr 은 첫 화면만 열리고 하위 주소는 404, nis.go.kr 은 500). 영상정보처리기기 망 구성 요구(전용망·망연계 방식)는 미확인.
- **옛 「지방자치단체 영상정보처리기기 통합관제센터 구축 및 운영규정」**: law.go.kr 행정규칙 한글주소로 찾아지지 않았다. 언론은 2013년 행정안전부 규정(제24조 교육 의무)으로 언급한다. 2026-05-11 고시는 "제정"으로 표시돼 있어 옛 규정을 개정한 것이 아니다. 옛 규정이 폐지됐는지, 병존하는지는 미확인.
- **TTA 「공공기관용 IP카메라/NVR 보안 성능품질 인증(TTA Verified)」**: TTA 인증 사이트(test.tta.or.kr 등)는 DNS 조회 실패, tta.or.kr 대표 누리집에서는 해당 메뉴를 찾지 못했다. 언론 보도 기준: 2018년 시작, 보안·기능·상호운용성 시험, 2023-07-01부터 공공 신규 계약에 인증 제품 요구, 2028-03-31까지 단계적으로 효력 종료. 모두 보조 출처.
- **국정원 보안기능 확인서의 영상정보처리기기 제품군**: 언론 보도 기준 2024-04-01부터 IP 카메라·영상정보 관리·저장 제품(NVR·VMS)이 대상, TTA 가 시험기관. KTR(시험기관) 페이지에서 제도 근거(국가정보원법 제4조, 전자정부법 제56조, 사이버안보업무규정 제9조)와 유효기간(국가용 보안요구사항 적용 시 5년)은 확인했으나, 그 페이지에 영상 제품군은 적혀 있지 않다.
- **스마트시티 통합플랫폼(112·119 연계)**: smartcity.go.kr 의 해당 글과 PDF 가 모두 404. 검색 요약으로만 5대 연계서비스(112센터 긴급영상 지원, 112 긴급출동 지원, 119 긴급출동 지원, 긴급재난상황 지원, 사회적 약자 지원)를 봤다. 연계에 쓰는 망·장비는 미확인.
- **개인정보위 「고정형 영상정보처리기기 설치·운영 안내서(2024.12.)」 본문**: 게시글만 확인, PDF 는 열지 않았다.
- **VLM 프레임 추출 방식**(구간 길이, 프레임 수): VSS 의 RT-VLM 세부 페이지가 소개 페이지로 넘어가 확인 못 했다.
- **RTSP 전송 계층**: RFC 7826 은 RTSP 메시지를 TCP(및 TLS over TCP)로 싣는다고 적는다. Axis 문서 요약은 "RTSP 554/UDP, RTSPS 322/UDP"로 나왔는데 요약 과정의 오류일 수 있다. 구성도에는 554/TCP 로 적는 것이 안전하다. RTP 영상은 UDP 가 보통이다(RFC 3550 1절).
- **PoE 전력 수치**(af 15.4W, at 30W, bt 60/90W 급): IEEE 페이지에는 수치가 없었다. 802.3bt 가 4쌍을 써서 전력을 늘렸다는 것만 확인. 802.3af/at 페이지는 열지 못했다.
- **NVR·DVR·비디오 인코더·함체·비디오 월·월 컨트롤러·서브 스트림·코덱·영상망·영상 반출**: 표준·공식 문서에서 정의를 확인하지 못해 용어 후보에 verified=false 로 넣었다. 아날로그 카메라·영상 디코더·비트레이트·프레임 추출·IGMP·RTCP 등은 60개 한도 때문에 후보에서 뺐다.
- **Milestone 포트 번호**: PDF 표를 글자로 뽑으며 열이 어긋났다. 7563(녹화 서버: 영상·음성·PTZ), 22331(이벤트 서버), 8081/8082(모바일 서버), 1433(SQL)은 문맥상 맞게 읽었으나 원문 표로 한 번 더 대조하는 것이 좋다.
- Milestone 외 VMS(Genetec, 한화비전 Wisenet WAVE, 국내 VMS)는 문서를 열지 않았다. "관리/녹화/이벤트 서버" 구분이 다른 제품에도 그대로 맞는지는 미확인.
- ONVIF Profile S 페이지는 코덱을 적지 않는다. "Profile S = H.264" 라는 통념은 확인하지 못했다.
