# 자원 한도 (개선 묶음 C)

2026-11-27 서비스 검토에서 나온 항목 가운데, 로그인한 한 계정(또는 MCP 키 하나)이 서버 자원을 끝없이 쓰는 길을 막는다.
묶음 A(보안 작은 고침, 같은 브랜치) 위에 얹는다.

## 왜

- 구성도 잠금이 호출마다 DB 연결을 새로 열어, 한 계정이 요청을 몰아 보내면 DB 연결이 바닥나 모두가 500 을 본다.
- 노드 설명·흐름 제안은 "계정당 동시 차례 2개" 밖이라, 한 계정이 Qwen 을 끝없이 병렬로 부를 수 있다.
- 명령의 글 길이와 구성도 크기에 상한이 없어 MCP 로 MB 단위 글을 넣을 수 있고, 버전마다 통째로 복사된다.
- MCP 주소는 키만 있으면 횟수 제한 없이 부를 수 있다(2026-11-10 에 "배포 때"로 미뤄 둔 것).

## 목표와 범위 밖

- 목표: 위 네 가지에 천장을 둔다. 평소 쓰임(탭 서너 개, 노드 60개쯤, Claude Code 로 그리기)은 걸리지 않는다.
- 범위 밖: 서버 전체의 Qwen 동시 호출 수(Clef 방식), 대화·질문 API 의 본문 크기, 서버 여러 대에서의 한도 공유.
- 하지 말 것: 한도에 걸린 요청을 500 으로 돌려주는 것. 모두 "바쁨"·429·413 처럼 이유를 알 수 있게 돌려준다.

## 접근

| 결정 | 고른 것 | 다른 길과 버린 이유 |
|---|---|---|
| 잠금 연결 (사용자 결정) | 잠금 전용 연결을 천장까지만 두고 빌려 쓴다 | DB 행 잠금 — 서버가 죽으면 만료까지 잠기고 갱신 로직이 필요하다. 계정별 한도만 넓히기 — 계정이 여럿이면 여전히 바닥난다. |
| 빌려 쓰는 방식 (내 판단) | 연결 하나짜리 클라이언트를 직접 돌려 쓴다 | postgres.js 의 `reserve()` — 빌린 연결이 끊기면 해제 쿼리가 처리되지 않는 예외로 멈춘다(테스트로 확인). |
| 배경 호출 한도 (사용자 결정) | 계정마다 배경 작업 한도를 따로 둔다(동시 3개) | 대화와 같은 2자리에 넣기 — 설명을 만드는 동안 대화가 막힌다. 서버 전체 한도 — 한 계정이 전체를 차지한다. |
| 자리가 없을 때 (내 판단) | 15초까지 기다리고, 그래도 없으면 바쁨 | 바로 거절 — 탭을 여러 개 연 사용자가 설명 실패를 보고 손으로 다시 시도해야 한다. |
| MCP 횟수 제한 (내 판단) | 서버 메모리에서 계정별로 센다(1분 120번) | `auth_attempts` 표 — 요청마다 DB 쓰기가 생긴다. 키별로 세기 — 키를 더 만들면 한도가 는다. |

## 항목

1. **잠금 전용 연결** (`chat/lock.ts`): 연결 하나짜리 클라이언트를 `DB_LOCK_POOL_MAX`(기본 20)개까지 두고 빌려 쓴다.
   - 다 쓰이고 있으면 `waitMs` 까지 기다리고, 그래도 없으면 연결을 더 열지 않고 `{ ok: false }`(바쁨). 1분에 한 번 경고를 남긴다.
   - 쥐고 있는 동안 닫히지 않게 postgres.js 의 유휴·수명 타이머는 끈다. 돌려받은 뒤 20초 쓰지 않으면 직접 닫는다.
   - 빌릴 때 먼저 `pg_advisory_unlock_all()` — 앞 차례가 해제에 실패해 남긴 잠금을 지운다.
   - 쉬는 동안 DB 가 끊은 연결은 첫 쿼리가 실패한다. 버리고 새 연결로 한 번 다시 한다.
2. **배경 작업 한도** (`chat/userTurns.ts` `withBackgroundSlot`): 설명 만들기와 흐름 제안의 "모델을 부르는 구간"만 감싼다.
   캐시로 답하는 설명 요청은 자리를 쓰지 않는다. 자리가 없으면 설명은 "여러 개 만들고 있어요", 흐름 제안은 기존 바쁨 문구(409).
   자동 흐름 제안은 다음에 다시 하도록 제안 시각을 되돌린다.
3. **글 길이** (`domain/commands.ts` `TEXT_LIMITS`): 이름 200자, 보조 글 300자, 속성 이름 60자·값 500자·50개, 가정 이름 80자·값 500자,
   흐름 단계 짧은 설명 200자, 연결 추정 20개.
4. **구성도 크기** (`domain/apply.ts` `STATE_LIMITS`): 영역 200, 노드 500, 연결 1500. 넘으면 그 추가 명령만 거절한다.
   이미 저장된 구성도에는 손대지 않는다(고치고 지우는 일은 한도와 무관).
5. **MCP 요청** (`api/mcp/route.ts`): 본문 1MB 초과는 413(길이 헤더를 믿지 않고 읽은 만큼 센다), 계정당 1분 120번 초과는 429 + `Retry-After`.
6. **E2E 설정** (`playwright.config.ts`): `TRUSTED_PROXY_HOPS=0`. main 의 "같은 IP 가입 5개" 제한 뒤로 E2E 는 여섯 번째 가입부터 막혔다.

## 확인

- 통합: 잠금을 되풀이해도 연결 수가 천장 안, 다 쓰이면 바쁨, 자리가 나면 다시 잡힘, DB 가 연결을 끊은 뒤에도 잡힘.
- 단위: 배경 한도(대화와 따로, 기다림·포기·끊김), 설명·흐름 제안의 바쁨 경로, 길이·개수 상한, MCP 413·429.
- `npm test`, `npm run test:int`, `npm run lint`, `npx tsc --noEmit`, E2E 전체.

## 배포할 때 볼 것

- DB 연결은 공용 풀 10개 + 잠금 20개까지 쓴다. DB 의 `max_connections`(기본 100) 안이면 된다.
- 로그에 `[lock] 잠금 전용 연결이 모두 쓰이고 있어…` 가 자주 보이면 `DB_LOCK_POOL_MAX` 를 올리거나 몰아 보내는 계정을 찾는다.
- 수치는 넉넉하게 잡은 어림값이다. 운영 DB 에서 가장 큰 구성도의 노드·연결 수를 한 번 확인해 두면 좋다.
