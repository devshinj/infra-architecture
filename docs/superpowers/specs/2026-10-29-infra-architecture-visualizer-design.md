# 인프라 아키텍처 시각화 도구 — 설계 문서

- 작성일: 2026-10-29
- 상태: 초안 (사용자 승인 대기)
- 표기: **[사용자 결정]** = 사용자가 직접 정한 것, **[설계자 판단]** = 대화 중 제안했고 사용자가 이의 없었던 것 또는 문서 작성자가 정한 것

---

## 1. 의도와 이유

### 1.1 이런 순간을 위해 만든다
1. **운영 중인 서비스 유지보수에 처음 투입될 때** — 코드·구성도가 흩어져 있거나 없어서 전체 그림을 잡기 어렵다. 아는 만큼 대화로 설명하면 AI 가 구성도로 정리해 준다.
2. **새 서비스를 개발할 때** — 코드 전에 인프라 큰 틀(서버·DB·캐시·외부 연동 등)을 먼저 잡고 싶다. "결제·카카오 로그인 붙는 쇼핑몰" 같이 말하면 초안을 그려 주고 대화로 다듬는다.

### 1.2 누구를 위한 것인가
- 지금: 사용자 본인 1명 (개인 도구). **[사용자 결정]**
- 나중: 팀 공유. 지금 구현하지 않지만, 로그인·공유를 나중에 붙이기 쉬운 구조여야 한다.
- 결과물(구성도와 설명)은 **비전공자도 이해**할 수 있어야 한다.

### 1.3 성공의 모습
- 대화 몇 마디로 그럴듯한 구성도가 **노드가 하나씩 나타나며 연결되는** 모습으로 그려진다.
- 노드를 누르면 "이게 뭔지 / 여기서 뭘 하는지 / 왜 골랐는지 / 누구랑 연결됐는지" 를 **짧고 명확하게** 바로 안다.
- 빠진 정보(스펙·IP·hostname·VIP·방화벽 등)를 도구가 먼저 알려 주고 채우도록 이끈다.

## 2. 목표 / 비목표 / 반목표

### 2.1 목표
- 대화형(GLM-5.3-Flash) 구성도 생성·수정
- 실시간(스트리밍) 렌더링: 노드가 하나씩 나타나고 연결선이 그어짐
- 연결 애니메이션 등 시각화 요소 (빠지면 안 됨) **[사용자 결정]**
- 노드/연결 설명 패널 (정의·역할·ADR·스펙·연관관계·연결 노드 링크, 용어 풀이)
- 영역(VPC/서브넷 등) 및 외부 서비스 묶음 표현
- 서버 상세 정보(스펙·OS·IP·hostname·VIP·방화벽) 와 빠진 정보 알림·가이드
- 표준 구성 패턴 지식 + 이상한 구성 경고
- 프로젝트별 관리: 구성도 여러 장, 대화 기록, 변경 이력

### 2.2 비목표 (이번 범위 아님, 나중을 위해 열어둠)
- 코드 저장소 / docker-compose / 클라우드 설정을 읽어 자동으로 그리기 **[사용자 결정: 나중]**
- 팀 공유·권한, 사내 Nexus 로그인 연동 **[사용자 결정: 나중]** (간단한 회원가입/로그인은 이번 범위, §10.2)
- 실제 인프라 배포(IaC 생성 등), 실시간 모니터링 연동

### 2.3 반목표 — 이렇게 되면 기능이 다 돼도 실패 **[사용자 결정]**
1. **설명이 길고 어려워 장황해지는 것.**
2. **캔버스가 엉켜** 노드 간 연결이 복잡해지고, 노드 안 글자를 알아볼 수 없게 되는 것.
3. (추가, 사용자 언급) 노드를 자유 드래그로 편집하게 만들어 조작이 복잡해지는 것.

## 4. 구성도 만들기·고치기

### 4.1 기본 원칙 **[사용자 결정]**
- **구조 변경은 대화로만**: 노드/연결 추가·삭제, 이름·스펙 수정은 전부 대화로 AI 가 수행.
- **위치 조정만 편집 모드에서**: "편집 모드" 를 켰을 때만 노드를 끌어 위치를 옮길 수 있다. 평소엔 캔버스가 잠겨 보기 전용(확대/축소/이동은 가능).
- 노드·연결을 수동으로 추가/삭제하는 캔버스 UI 는 만들지 않는다.

### 4.2 자동 배치 **[설계자 판단]**
- LLM 은 좌표를 정하지 않는다. "무엇이 무엇과 어떻게 연결되는지" 만 만든다.
- 배치는 자동 배치 엔진(ELK.js layered)이 계층 순서(사용자 → 진입(LB 등) → 앱 서버 → 데이터)와 중첩 영역을 고려해 결정.
- 편집 모드로 옮긴 위치는 저장되며, 이후 AI 가 구조를 바꿀 때도 가능한 한 유지(고정 노드로 취급)하고 새 노드만 배치한다. 사용자가 "자동 정렬" 버튼으로 다시 전체 배치 가능.

### 4.3 실시간 생성 **[사용자 결정]**
- AI 응답이 오는 동안 변경 명령이 하나 도착할 때마다 캔버스에 반영: 노드는 나타나는 애니메이션, 연결선은 그어지는 애니메이션.
- 대화창에는 진행 상황이 한 줄씩 표시 ("L7 로드밸런서 추가…", "캐시·DB 연결…").
- 완료 시 요약 ("노드 8, 연결 7") 과 함께 연결선의 데이터 흐름 애니메이션 시작.
- 생성 도중 배치가 계속 흔들리지 않도록, 스트리밍 중엔 임시 배치 → 완료 시 최종 배치로 부드럽게 이동하는 방식을 권장. 구체 방식은 구현자 재량.

### 4.4 노드 참조 **[사용자 결정]**
- 모든 노드(와 연결선, 영역)는 고유 ID 를 가진다.
- 노드 우클릭 메뉴 또는 "노드 링크 복사" 버튼 → 대화 입력창에 `@WAS#1` 형태의 참조 칩이 삽입됨.
- 사용자가 "@WAS#1 메모리 32GB 로 올려줘" 라고 하면 AI 는 그 ID 의 노드를 정확히 수정.

### 4.5 LLM 연동 **[사용자 결정: 사내 vLLM, OpenAI 호환 API]**
- 모델: GLM-5.3-Flash. 사내 서버의 vLLM 이 OpenAI 호환 API 로 제공.
- 주소·모델명·(있다면) API 키는 설정(환경변수 또는 설정 화면)으로 받는다.
- AI 는 구성도를 **작은 변경 명령의 연속**으로 출력한다. 명령 예:
  - `add_group`(영역/외부 서비스), `add_node`, `add_edge`, `update_node`, `update_edge`, `remove_node`, `remove_edge`, `set_explanation`, `report_missing`, `warn`
- 전달 방식 두 가지를 모두 지원 **[설계자 판단, 사용자 동의]**:
  1. **Tool calling (기본)**: 함수 호출로 명령 수신. 사용자 측 에이전트 확인 결과 동작하는 것으로 보이나 서버 플래그는 미확인.
  2. **JSON Lines 폴백**: 한 줄에 명령 하나씩 JSON 으로 출력하게 하고 줄 단위로 파싱.
  - 연결 시 지원 여부를 한 번 자동 확인하고 방식을 고른다. 화면상 동작은 두 방식이 동일.
- 모든 명령은 스키마 검증 후 적용. 잘못된 명령(없는 노드 ID 참조 등)은 버리고 대화창에 조용히 알림 또는 AI 에 재요청.
- 대화 맥락에는 현재 구성도 상태(노드·연결·ID)를 요약해 함께 보낸다.

## 5. 캔버스 표현

### 5.1 요소
- **노드**: 아이콘 + 이름 + 짧은 부제(SW 이름, 대수 등). 예: `🖥️ API 서버 / Spring ×2`.
- **영역(그룹)**: 우리 서비스 영역(예: AWS VPC, IDC), 그 안의 공개/내부 구역(서브넷, DMZ 등). 중첩 가능.
- **외부 서비스**: 점선 큰 상자(예: 결제대행사, 카카오 로그인). **[사용자 결정]** 내부 구성을 알면 상자 안까지, 모르면 우리와 닿는 접점(결제 승인 API, Webhook, OAuth 서버 등)까지만 그린다.
- **이중화 묶음**: VIP 로 묶인 이중화 쌍(WEB#1/#2, DB Active/Standby 등)을 하나의 묶음 테두리 + VIP 라벨로 표현.
- **연결선**: 방향, 방식 라벨(HTTPS, TCP 6379, Webhook, 복제 등). 외부와 오가는 선은 색을 구분. 동기 요청과 비동기 알림은 선 모양(실선/점선) 구분.
- **방화벽**: 구간 사이 방화벽 필요 여부/규칙을 연결선 또는 영역 경계에 표시.

### 5.2 애니메이션 **[사용자 결정: 필수]**
- 생성 시: 노드 등장, 선 그어짐.
- 평상시: 연결선 위로 데이터 흐름(움직이는 점선/점) 애니메이션.
- 선택 시: 선택 노드와 이어진 연결선 강조, 나머지는 흐리게.
- 애니메이션 끄기 토글 제공 **[설계자 판단]**.

### 5.3 가독성 규칙 (반목표 2 대응, 품질 기준) **[설계자 판단]**
- 연결선이 노드를 가로지르지 않는다(직교 라우팅 권장).
- 노드 안 글자는 잘리지 않으며, 기본 확대 배율에서 읽을 수 있는 크기 이하로 줄이지 않는다.
- 라벨끼리, 라벨과 노드가 겹치지 않는다.
- **규모: 구성도 한 장에 노드 30~100개가 흔함 [사용자 결정]** → 아래가 필수:
  - **영역 접기/펼치기**: 접힌 영역은 하나의 노드처럼 보이고 내부 노드 수를 표시. 접힌 영역으로 들어가는 연결선은 묶어서 한 줄로 표시.
  - 노드가 많을 때(대략 40개 초과, 구현자 조정) 처음 열면 하위 영역을 접은 개요 상태로 시작.
  - 이중화 쌍(WEB#1/#2 등)은 묶음으로 접어 "WEB ×2" 로 보일 수 있다.
  - 확대 배율이 낮을 때는 노드 부제·연결 라벨을 숨기고 이름만 표시(단계별 상세).
  - 데이터 흐름 애니메이션은 노드가 많을 때 선택된 경로만 재생하는 등 성능을 지킨다.
- 이 규칙들은 구현 후 대표 구성(§7.1 패턴들)과 노드 100개 규모 샘플로 확인한다.

## 6. 설명 패널 (ℹ️ 설명 탭)

### 6.1 일반 노드 **[사용자 결정]**
순서대로:
1. **이름 + 분류** (예: `⚡ Redis` · 캐시 / 인메모리 저장소)
2. **정의 (한 문장)**: 정식 명칭·약어 풀이와 분류를 포함한 사전식 정의. 비유 쓰지 않음.
   예: "Redis(Remote Dictionary Server)는 데이터를 디스크가 아닌 메모리에 저장해 빠른 읽기와 쓰기 속도를 제공하는 인메모리 NoSQL 키-값(Key-Value) 데이터 구조 스토어입니다."
3. **이 구성에서의 역할**: 일반론이 아닌 이 프로젝트에서의 역할, 1~2 문장.
4. **ADR 요약**: 결정 / 이유 / 대안 / 대가 각 한 줄.
5. **스펙 / SW**: 버전, CPU·RAM·디스크, OS, 대수 등.
6. **서버 정보** (해당 시): hostname, IP, VIP.
7. **연관관계**: 누가 누구를 어떤 방식(프로토콜·포트)으로 부르는지.
8. **연결된 노드**: 칩 목록, 클릭 시 캔버스에서 그 노드로 이동·선택.

### 6.2 용어·약어 노드 (예: L4 로드밸런서) **[사용자 결정]**
- **용어 정의** (예: "L4란? 네트워크 7계층 중 4번째(전송 계층). IP·포트만 보고 트래픽을 나눔")
- **필요한 이유** (간단히)
- **비교** (예: L4 vs L7)

### 6.3 연결선 선택 시 **[설계자 판단]**
- 무엇이 오가나 / 방식(프로토콜·포트·동기/비동기) / 왜 연결됐나 / 방화벽 규칙.

### 6.4 본문 속 용어 풀이 **[설계자 판단, 사용자 유지 동의]**
- 설명 본문의 전문 용어(세션, Cache-aside 등)는 점선 밑줄 표시, 마우스 올리면 한 줄 풀이.

### 6.5 길이 규칙 (반목표 1 대응) **[사용자 결정: 짧게 / 상한 수치는 설계자 판단]**
- 정의 1문장, 역할 1~2문장, ADR 각 항목 1줄, 용어 풀이 1문장.
- 항목별 글자 수 상한을 두고(대략 정의 120자, 역할 150자, ADR 항목 80자 내외 — 구현자가 조정 가능), 초과 시 AI 에 짧게 다시 쓰도록 재요청.
- 설명은 AI 가 생성하며, 사용자는 대화로 수정 요청할 수 있다.

### 6.6 설명 생성 시점 **[설계자 판단]**
- 구성도 스트림에는 구조 명령(노드·연결·영역·속성)만 넣어 "하나씩 나타남" 속도를 지킨다. 설명은 스트림에 넣지 않는다.
- 구조 스트림이 끝나면 노드별 설명을 백그라운드에서 생성해 캐시한다. 생성 전에 노드를 누르면 그 노드를 우선 생성한다(로딩 표시). 용어 사전에 있는 정의는 즉시 표시한다.
- 노드의 종류·SW·연결이 바뀌면 그 노드(와 연결 상대)의 설명 캐시를 무효화하고 다시 생성한다.
- 글자 수 초과 재작성은 이 설명 생성 단계에서만 일어난다.

### 6.7 설명의 출처와 용어 사전 **[사용자 결정: DB 용어 사전, 자동 추가 + 미검수]**
- 용어 사전은 **DB 테이블**로 관리한다. 항목: 용어, 정식 명칭/약어 풀이, 분류, 한 문장 정의, 필요한 이유, 비교 대상, 검수 상태, 출처(초기/AI).
- 초기 데이터: 구현자가 자주 쓰는 SW·용어 50개 안팎의 한국어 초안을 시드로 넣는다(Redis, Nginx, L4/L7, VIP, NAT, DMZ, CDN, Kafka 등). 시드도 처음엔 "미검수" 상태로 두고 사용자가 검수한다. **[설계자 판단]**
- 노드 정의는 사전에 있으면 사전에서 즉시, 없으면 AI 가 생성하고 **그 결과를 사전에 자동 추가하며 "미검수" 배지**를 붙인다.
- **용어 사전 화면**: 목록·검색·수정·검수 완료 처리. 설명 패널의 미검수 정의 옆에 배지 표시.
- "이 구성에서의 역할 / ADR" 은 프로젝트 맥락이므로 사전이 아니라 노드별로 AI 가 생성.
- 구성 패턴·경고 규칙은 리포지토리 데이터 파일로 관리(§10). **[설계자 판단]**

## 7. 지식: 구성 패턴과 경고

### 7.1 구성 패턴 라이브러리 **[사용자 결정: WEB-WAS-DB 외 다양한 패턴 / 목록은 설계자 판단]**
최소 포함 후보:
- WEB-WAS-DB 이중화 (VIP, DB Active/Standby, DB 중계/복제)
- L4/L7 로드밸런싱 + 오토스케일링
- 캐시 계층 (Redis, Cache-aside)
- 메시지 큐 기반 비동기 처리 (Kafka/RabbitMQ)
- Kubernetes 클러스터 (Ingress, Service, Pod)
- CDN + 정적 호스팅
- 서버리스 (API Gateway + 함수)
- DR(재해복구) 구성 (멀티 AZ/리전)
- 외부 연동 (PG, OAuth 소셜 로그인)

용도: AI 프롬프트의 기준 지식, 초안 생성의 출발점, 경고 판단 기준.

### 7.2 이상한 구성 경고 **[사용자 결정]**
- 구성이 표준 패턴에서 위험하게 벗어나면 대화와 설명 패널에서 경고 + 가이드 제공.
- 예: DB 가 공개 구역에 있음, 단일 장애점(1대뿐인 핵심 서버), 외부→내부 직접 접근에 방화벽 없음, 캐시만 있고 원본 DB 없음.
- 확실한 규칙은 코드 규칙 검사로, 애매한 판단은 AI 로. **[설계자 판단]**
- 경고는 강요가 아니라 제안: 사용자가 "의도된 구성" 으로 무시 처리 가능.

## 8. 빠진 정보 채우기 **[사용자 결정: B안 + 대화 연동]**

### 8.1 대상 항목
서버형 노드 기준: hostname, CPU, RAM, 디스크, OS, IP, VIP(이중화 묶음), SW/버전. 구간 기준: 방화벽 필요 여부·포트. DB 기준: 복제 방식(동기/비동기). 노드 종류별 필요 항목은 노드 타입 정의에서 정한다(구현자 재량으로 확장).

### 8.2 동작
- 구성도가 그려지거나 바뀌면 빈 항목을 계산.
- **노드 배지**: 노드 오른쪽 위에 빈 항목 수(빨간 숫자).
- **체크리스트 알림**: 대화 탭 상단에 "🔔 채워야 할 정보 (N)". 펼치면 노드/구간별로 빈 항목 + 입력 폼. "모름" 표시 가능(카운트에서 빠지되 표시는 남음).
- 노드 배지 클릭 → 해당 항목으로 이동.
- **대화에서도 알림**: AI 응답 끝에 "빠진 정보 N개가 있어요" 한 줄.
- **"대화로 물어보기" 버튼**: 체크리스트에서 누르면 AI 가 해당 항목들을 하나씩 질문하는 가이드 대화 시작. 답을 받으면 해당 필드에 반영.
- 폼에 직접 입력한 값도 구조 변경과 동일하게 변경 이력에 남는다. (폼 입력은 "구조"가 아닌 "속성 값 입력"이므로 §4.1 의 대화 전용 원칙의 예외로 허용 — 사용자가 B안을 고름) **[설계자 판단]**

## 9. 프로젝트 관리 **[사용자 결정]**

- **프로젝트** ⊃ **구성도 여러 장** (예: 운영/개발/DR, 현재/개선안)
- 구성도마다 **대화 기록** 보관. **[설계자 판단: 대화는 구성도 단위]**
- **변경 이력**: AI 변경 1회(응답 1번) 또는 폼 입력 저장 1회마다 버전 1개 자동 생성. 버전 목록 보기, 이전 버전 보기, 되돌리기, 두 버전 비교(추가/삭제/변경 노드 색 표시). **[설계자 판단: 이력 단위·비교 기능]**
- **되돌리기는 비파괴적**: 이전 버전으로 되돌리면 그 내용으로 새 버전이 생긴다(기존 이력은 삭제하지 않음). 대화는 이어지며, 대화창에 "v3 로 되돌림" 시스템 메시지를 남기고 AI 맥락에도 현재 상태를 다시 전달한다. 각 버전은 그 버전을 만든 대화 메시지와 연결된다. **[설계자 판단]**
- **응답 중단 처리**: AI 응답이 오류·사용자 중단으로 끊기면 그때까지 적용된 변경을 "중단됨" 표시가 붙은 버전으로 남긴다(사용자가 그 자리에서 되돌릴 수 있음). **[설계자 판단]**
- 프로젝트·구성도 생성/이름 변경/삭제/복제.

| 영역 | 선택 | 근거 |

| DB | PostgreSQL (처음부터) — **[사용자 결정]**, 로컬은 Docker | 팀 공유 대비 |
| ORM | Drizzle — **[설계자 판단]** | |
| 저장 형태 | 구성도 버전은 JSON 스냅샷 — **[설계자 판단]** | 이력·비교·되돌리기 단순화 |
| 지식 | 구성 패턴·경고 규칙은 리포지토리 데이터 파일, 용어 사전은 DB 테이블(§6.7) | 프롬프트·규칙검사 공용 |
| 인증 | Auth.js (NextAuth) — **[사용자 결정]** | 지금은 Credentials, 나중에 Nexus provider 추가 |

### 10.1 실행 환경 **[사용자 결정]**
- 사내 서버에 배포해 브라우저로 접속. 사내 vLLM 접근 가능한 망. PostgreSQL 도 서버 측에 둔다(로컬 개발은 Docker).
- vLLM 주소·모델명·키, DB 접속 정보, SMTP 정보는 환경변수로 받는다. **[설계자 판단]**

### 10.2 로그인·회원 **[사용자 결정]**
- 회원가입: 아이디, 비밀번호, 이메일(비밀번호 찾기용).
- 로그인: 아이디 + 비밀번호. 비밀번호는 해시 저장.
- 비밀번호 찾기: 이메일로 재설정 링크 발송. SMTP 설정이 없으면 재설정 링크를 서버 로그에 남기는 개발용 대체 동작. **[설계자 판단]**
- 나중에 사내 Nexus 로그인으로 연동 예정 → 인증은 Auth.js provider 교체/추가로 끝나도록, 사용자 테이블에 외부 계정 연결(accounts) 구조를 둔다.
- 프로젝트는 소유자(사용자)를 가지며, 지금은 본인 프로젝트만 보인다. 팀 공유(멤버·권한)는 나중. **[설계자 판단]**

### 10.3 LLM 호출 제약 **[사용자 제공 정보]**
- GLM-5.3-Flash: 컨텍스트 1M(입력+출력 ≤ 1M), 공식 출력 상한 128K. 서빙 레벨에서 출력 캡이 없을 수 있으므로 **클라이언트에서 `max_tokens` ≤ 131072 로 항상 지정**.
- 권장 파라미터: temperature 1, top_p 0.95, reasoning_effort max. **추론(reasoning)은 항상 켜져 있고 끌 수 없음** →
  - 첫 명령이 오기 전 사고 시간이 생긴다. 대화창에 "구성 검토 중…" 상태를 표시해 멈춘 것처럼 보이지 않게 한다.
  - 설명 생성처럼 가벼운 작업에는 더 낮은 reasoning_effort 를 쓸 수 있는지 구현 시 확인(가능하면 적용).
  - temperature 1 로 출력 형식이 흔들릴 수 있으므로 명령 스키마 검증 + 재요청은 필수.
- 멀티모달(이미지 최대 16장) 지원. 이미지 입력은 현재 범위 아님(나중에 "기존 구성도 이미지 넣어 그리기" 확장 여지).
